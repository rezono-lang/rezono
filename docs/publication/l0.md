# Publication 1.0 (L0)

This document describes publication format 1.0, also called L0. It agrees with the reference code in `publication/rezono_publication/`, the conformance cases in `docs/publication/cases/`, the tests in `publication/tests/` and the contracts in `contracts/`. Where those sources do not settle a point, the text says "open". Section numbers are those the repository cites.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope

L0 defines how a dataset and its schema are published so that a third party can read, check and hash them.

A publication has five parts.

- A schema document (section 2).
- Rows in Row JSON (section 3).
- A columnar form in Apache Arrow and Apache Parquet (section 4).
- An RDF view (section 5).
- Logical hashes (section 6).

Section 7 names the forms and their media types. Section 8 describes the conformance cases.

A **reader** takes input and either accepts it or rejects it with an error. A reader never converts. It does not turn a float into an integer. It does not guess a state. It does not rewrite text that is not in its normal form.

A **verifier** is a reader that also classifies the change from one schema to its successor (section 2.4).

A reader or verifier needs only this document and Rezono's canonical JSON. It does not need the compiler, the publisher or the rule engine. This is the scope rule: the reference reader (`publication/rezono_publication/l0.py`) imports none of them.

An error names the element and the rule it breaks.

### Conventions

JSON is RFC 8259 JSON. Row JSON and schema documents are read as I-JSON (RFC 7493) with these extra rules.

- `null` is refused everywhere.
- A JSON number with a fraction or exponent is refused, also `1.0` and `1e1`.
- `-0` as a JSON number is refused.
- A duplicate object key is refused.
- A lone surrogate in a string is refused.
- A byte order mark at the start of the text is refused.

Canonical JSON is the one canonical form of Rezono. It follows RFC 8785 (JSON Canonicalization Scheme) over values that have no numbers. An integer is written as decimal text. A date or a UTC time is written as ISO text. Object keys are sorted by UTF-16 code units. A value with no single canonical form (a float, `null`, a lone surrogate, a naive time) has no canonical JSON.

`H(x)` is the SHA-256 digest of the canonical JSON of `x`, as 64 lower-case hex digits. `CJ(x)` is the canonical JSON of `x` as text.

Identifiers in this format:

| Identifier | Form | Meaning |
|---|---|---|
| Schema id | `s-<64 hex>` | `H` of a schema document |
| Dataset hash | `d-<64 hex>` | the logical hash of a dataset |
| Definition hash | `c-<64 hex>` | the logical hash of the control kinds of a dataset |
| Manifest id | `m-<epoch>` | an epoch, with `<epoch>` a natural number |
| Pack name | `[a-z][a-z0-9]*(-[a-z0-9]+)*` | a pack |
| Kind name | `[A-Z][A-Za-z0-9]*` | a kind or a local type |
| Code | `[a-z][a-z0-9_]*` | a reason code |

## 2. The schema document

A schema document is a JSON object. A reader accepts it with the rules below and returns its schema id.

Every integer in a schema document is decimal text. A JSON number is refused. `null` is refused. A boolean is allowed only as the value of a `derived` member.

The top-level members are the following. Any other member is refused.

| Member | Required | Meaning |
|---|---|---|
| `rezono` | yes | the format version, the text `"1.0"` |
| `pack` | yes | the pack name |
| `base` | yes | an absolute IRI that ends in `/` |
| `kinds` | yes | an object of kinds |
| `types` | no | local types |
| `enums` | no | enumerations |
| `imports` | no | pinned imports of other packs |
| `map` | no | external IRIs for kinds and slots |
| `reasons` | no | declared reason codes |
| `follows` | no | the schema id of the schema this one succeeds |

A reader that does not implement versioned kinds (section 3.6) MUST reject a schema that has a `versioned` member. It MUST NOT ignore the member.

### 2.1 Kinds, slots and types

#### Kinds

A kind is an object. Its members are `world`, `id`, `slots`, `iri`, `parent`, `versioned`, `applies`, `plane`, `owner` and `tuple_key`. Any other member is refused.

- `world` is required, with no default. It is `open` or `closed`. A closed kind lists all its elements. An open kind may have elements the dataset does not list.
- `id` is required and has exactly one member, `type`. It names the type of the element id. An id is text in the normal form of that type. A `Bool` is not an id type. An `Integer` id is always written as text.
- `slots` is required. It may be `{}`.
- `iri` is optional. It is an absolute IRI with no `#` and no `?`, and it does not end in `/`. The default is `<base><Kind>`.
- Two kinds MUST NOT have the same IRI. The element IRI of a kind is built from it (section 3.4), so it names one kind.

The kinds of one schema are the keys of `kinds`. A kind name is PascalCase.

#### Slots

A slot name does not start with `$` or `@`.

A slot has these members. Any other member is refused.

| Member | Meaning |
|---|---|
| `type` | the type name of the value |
| `ref` | the kind name of a reference |
| `card` | `1`, `?`, `*` or `+` |
| `states` | the states the slot may be in |
| `world` | `open` or `closed`, for a many-valued slot, stated against the kind's own world |
| `derived` | a boolean; true when the value is derived, not stated |
| `inverse` | text; marks the slot as the inverse of another |
| `min`, `max` | exact decimal text |
| `backfill` | a state object, for a slot added later (section 2.4) |
| `versions` | the definition versions of a derived slot (section 3.6) |
| `expr` | text; the expression of a derived slot or a shown value |

A slot has exactly one of `type` and `ref`.

`card` is the number of values. `1` means exactly one. `?` means at most one. `*` means any number. `+` means at least one. A slot with `card` `*` or `+` is many-valued.

`states` is a non-empty list of distinct states. It includes `known`. The states are listed in code order: `known`, `not_applicable`, `unknown`, `invalid`.

`ref` names a kind of this schema, or `<prefix>.<Kind>` for a kind of an imported pack. A prefix MUST be declared in `imports`.

A slot with `inverse` is the same relation as its forward slot. A writer does not write it as data and a reader refuses a row that does. It has no column and no table.

#### Types

A slot `type` is a core type, a local type declared in `types`, or `<prefix>.<Type>` for a type of an imported pack.

The core types are `Text`, `Bool`, `Integer`, `Ratio`, `Date`, `DateTime`, `Quantity`, `Money`, `Period` and `Enum`.

A local type is an object with `of`, which names a core type. A local type name is PascalCase and is not a core type name. The members each core type may carry are:

| `of` | Members |
|---|---|
| `Text` | `pattern`, `normalize`, `fields` |
| `Bool` | none |
| `Integer` | `min`, `max` |
| `Ratio` | `min`, `max` |
| `Date`, `DateTime` | none |
| `Quantity` | `dimension`, `unit`, `storage_unit`, `factor`, `scale`, `min`, `max` |
| `Money` | `currency`, `scale`, `per` |
| `Period` | `over`, `range` |
| `Enum` | `enum` |

Every local type may also carry `storage`, an Arrow type name (section 4.4). It overrides the storage a reader computes.

Rules:

- `min`, `max` and `factor` are exact decimal text or `n/d`. For an `Integer`, `min` and `max` are integer text.
- `scale` is a natural number as text.
- `normalize` is a list. Each entry is `uppercase`, `lowercase`, `strip spaces` or `trim`.
- `pattern` is a regular expression that compiles.
- `Quantity` requires `unit` and `storage_unit`.
- `Money` requires `currency`, an ISO 4217 code of three upper-case letters.
- `Period` requires `range`, `closed` or `half_open`, and `over`, an ordered type. `over` is not a `Period`, `Bool`, `Text` or `Enum`.
- `Enum` names an enumeration declared in `enums`.

An enumeration is a list of distinct values (a closed enumeration), or `{"world": "open", "values": [...]}` (an open enumeration).

#### Imports

`imports` maps a prefix to a pinned pack: `{"pack", "schema", "manifest", "dataset"}`.

- `pack` is a pack name.
- `schema` is a full schema id. It MUST be a full id, not a prefix of one.
- `dataset` is a full dataset hash.
- `manifest` is a manifest id.
- `manifest` without `dataset` is refused: an epoch pin needs its hash pin.

#### Maps

`map` maps a kind name, or `Kind.slot`, to an absolute IRI. The kind or slot MUST exist. A slot restated by a subkind is one property, so it is mapped on the kind that declares it.

#### Derived tuples

A kind of derived tuples MAY name its column order in `tuple_key`. It lists every slot of the kind exactly once. Each such slot is `derived: true`, `card` `1`, states `["known"]`, and has no `inverse`, `versions`, `backfill` or `expr`. The kind has no `parent`, `versioned` or `plane`. Its id type is plain `Text`.

The `$id` of a row of that kind is the canonical JSON of the list of its cells, in `tuple_key` order. A cell is the payload text, or the target id for a reference. A reader checks the `$id` against the cells.

#### 2.1.1 Kind trees

A kind MAY name another kind in `parent`. The kind is then a subkind.

- `parent` names a kind of the same schema.
- No kind is above itself: `parent` makes a tree.
- A subkind and its parent are not versioned.
- A subkind has the same `id` as its parent.
- A subkind restates every slot of its parent. The restated slot equals the parent's, except for `world`. So the `slots` of a kind are all the slots of its rows.

An element of a subkind is also an element of every kind above it. A dataset writes it once, at its most specific kind, with every slot (section 3.1). The tree shares one IRI space, that of its root (section 3.4).

A slot restated by a subkind is the same property as the one declared by the highest kind of the chain.

### 2.2 Schema identity

The schema id is `"s-" + H(document)`. The hash is over the whole document, as read. Member order and white space do not change it. `follows`, `map`, `reasons`, `plane` and `owner` are part of the document, so a change in any of them changes the id.

A schema id is not shortened anywhere in the format. An import and a `$schema` member carry a full id.

A publisher MUST write the schema document in canonical JSON. These bytes are the ones the id hashes.

### 2.3 Reasons

A state in a row carries a reason (section 3.3). A reason is text. It is empty, or it is a reason code.

The core reason codes are always in scope. A schema need not declare them. Each may label only some states.

| Code | States it may label |
|---|---|
| `no_version_applies` | `unknown` |
| `versions_overlap` | `invalid` |
| `exception_conflict` | `invalid` |
| `no_row_applies` | `unknown` |
| `ambiguous_date` | `invalid` |
| `empty` | `not_applicable` |
| `no_value` | `not_applicable`, `unknown` |
| `no_match` | `not_applicable`, `unknown` |
| `multiple_values` | `invalid` |
| `added_later` | `not_applicable`, `unknown`, `invalid` |

A schema MAY declare more codes in `reasons`. Each entry has two members, both required.

- `label` maps a language tag to non-empty text. It has an `en` entry. A language tag is a BCP 47 tag, checked by its shape.
- `states` lists the states the code may label. It is in code order and does not contain `known`.

A schema MAY restate a core code in `reasons`. Its `states` are then a subset of the core states.

A reader applies these rules to a reason on a state object.

- An empty reason is always accepted.
- A reason that is not a code is refused.
- A core code is refused on a state it may not label.
- If the schema has no `reasons` member, a code of the right form is accepted.
- If the schema has `reasons`, a code that is not core MUST be declared, and its `states` MUST include the state it labels.

A schema that adds `reasons` to one that had none is a change that can narrow what a reader accepts. Section 2.4 classifies it.

### 2.4 Change classes

A verifier classifies the change from a schema A to its successor B. The class is one of `patch`, `minor`, `major` and `invalid_successor`. The class of a change with several parts is the highest of its parts, in the order `patch` < `minor` < `major` < `invalid_successor`. The verifier reports the reasons that set the class.

Both A and B MUST be accepted schema documents.

A change is a **patch** when it cannot change what a reader accepts or what a dataset hashes to. A **minor** change widens what a reader accepts. Rows of A are still read under B. A **major** change may narrow it. An **invalid successor** adds a slot without a `backfill`.

| Change | Class |
|---|---|
| no difference | patch |
| `follows` changes | patch |
| any other top-level member changes (`rezono`, `pack`, `base`) | major |
| a `map` entry is added | patch |
| a `map` entry changes or is removed | major |
| an import is added | minor |
| an import changes or is removed | major |
| an enumeration is added | minor |
| values are appended to an open enumeration, keeping the order of the old values | minor |
| any other change to an enumeration, or its removal | major |
| a local type is added | minor |
| a local type is removed | major |
| a bound of a type is widened (`min` lowered or `max` raised) and its storage and integer spelling stay the same | minor |
| a bound is widened but the storage or the integer spelling changes | major |
| any other change to a type | major |
| `reasons` is introduced and lists every code (with its state) that the datasets of the lineage use | minor |
| `reasons` is introduced and leaves such a code out | major |
| `reasons` is removed | major |
| a reason code is added | minor |
| a reason code is removed | major |
| the states of a reason code change | major |
| only the label of a reason code changes | patch |
| a kind is added | minor |
| a kind is removed | major |
| the `owner` of a control kind changes | patch |
| any other member of a kind changes (`world`, `id`, `iri`, `parent`, `versioned`, `plane` and so on) | major |
| a slot is added with a `backfill` | minor |
| a slot is added without a `backfill` | invalid successor |
| a slot is removed | major |
| a version is appended to the `versions` of a derived slot | minor |
| a bound of a slot is widened | minor |
| any other change to a slot | major |

The "lineage's datasets" are the datasets published under the schema chain. The caller passes them to the verifier.

The boundary of integer storage is part of the class. Widening `max` of an `Integer` from 1000 to 10 000 000 000 000 000 moves it out of the range of a JSON number (section 3.2) and the storage `int64` (section 4.4), so the change is major.

A reader reads rows of A under a minor or patch successor B by giving each added slot its `backfill` state. A reader MUST refuse to do so for a successor that is major or invalid.

### 2.5 Data contracts

A data contract describes the columnar form (section 4) of a schema to a tool that does not know L0. It is made from the schema document alone, for example as an Open Data Contract Standard (ODCS) document. The contract is derived. It is not a source of truth: the schema document is.

A data contract states, for each table of the columnar form:

- the table and its columns (section 4.1);
- the physical type of each column, in the spelling of section 4.4;
- whether a column may be null;
- the key columns, which are the primary key, in column order;
- quality rules for what a column type cannot say: the state codes a slot allows, a null exactly beside a state, a reason beside the state it may label, the pattern of a text type, the values of a closed enumeration, the bounds of integers, quantities and money, and the members of a set (at least one for `+`);
- a foreign key for a reference to a kind of the same pack;
- the metadata of section 4.2 and the extensions of section 4.5 as custom properties.

A contract's version is the schema id, with the pins it was given (section 6.4). Its identifier is the schema's `base`, so it is the same for every schema of a lineage.

What a contract cannot say is listed in its loss list (`odcs.losses.yaml`). Which ODCS version and which field mapping a publication settles on is open (Q12).

## 3. Row JSON

Row JSON is the form of a dataset as JSON. Every row is a JSON object.

A reader reads rows under an accepted schema. This is a dataset reader. It refuses text that is not in its normal form. A reader that accepts lenient input in a delta profile (section 7) is not specified here (open).

### 3.1 The collection

A **row** has `$kind`, `$id` and one member for each slot of the kind. It MAY have `$schema`, `$why`, `$src`, `$valid`, `$known` and `@context`. Any other `$`-member is refused. Any other `@`-member is refused. A member that is not a slot and does not start with `$` or `@` is refused.

- `$kind` is the name of a kind of the schema.
- `$id` is non-empty text in the normal form of the id type of the kind.
- `$schema`, if present, is a full schema id and equals the id of the schema the reader reads under.
- Every slot is present. Absence is a state, written explicitly (section 3.3). A slot with `inverse` is never present.

A **collection** is the object `{"$schema": "s-…", "$rows": [...]}`. It MAY also have `@context`. `$schema` is required and equals the id of the schema read under. Any other member is refused.

A collection MUST NOT hold two rows with one key. The key of a row is `($kind, $id, $valid, $known)`. For a kind that is not versioned, `$valid` and `$known` are empty.

One id names one element in a kind tree (section 2.1.1). A row of a subkind and a row of a kind above it with the same `$id` are refused. The element is written once.

**JSON Lines** is the same set of rows as lines. The first line is the header `{"$schema": "<schema id>", "rezono": "1.0"}`. Each other non-empty line is a row. A reader reads it as the collection of the same rows.

A reader MUST parse the text as in section 1. It refuses duplicate keys, floats, `null`, lone surrogates, a byte order mark and `-0`.

### 3.2 Values

A **payload** is the exact value a reader derives from a known value. Columns and hashes hold payloads. A known value MUST be in the normal form of its type. A reader checks the form and never rewrites it.

| Type | Row JSON value | Payload |
|---|---|---|
| `Text` | a string, already in its normal form | the string |
| `Bool` | `true` or `false` | the boolean |
| `Integer` | see below | integer text |
| `Ratio` | `n` or `n/d` as text, in lowest terms | the text |
| `Date` | `YYYY-MM-DD`, a calendar date | the text |
| `DateTime` | `YYYY-MM-DDTHH:MM:SS[.f]Z`, UTC | the text |
| `Quantity` | `<number> <unit>` | the stored integer, as text |
| `Money` | `<currency> <amount>[/<per>]` | the stored integer, as text |
| `Period` | `a..b` or `a..<b` | `{"from", "to"}` |
| `Enum` | a string | the string |
| a reference | `{"$ref": "<id>"}` | the target id |

Details:

- **Text.** With `normalize`, the value MUST equal the result of applying each step to itself. With `pattern`, the whole value MUST match.
- **Integer.** An integer is written as a JSON number when its type declares `min` and `max` and both are within plus or minus (2^53 - 1). Otherwise it is written as a JSON string. This is rule LD2. A value in the wrong spelling is refused. The text is the shortest decimal form: `0`, or a non-zero digit first, with an optional `-`. `-0` is refused. Bounds of the type and of the slot are checked.
- **Ratio.** The text `n` or `n/d`. `d` is at least 2 and `n/d` is in lowest terms. `-0` is refused. Bounds are checked.
- **DateTime.** The fraction has 1 to 6 digits and no trailing zero. An absent fraction is written without the dot.
- **Quantity.** The number is the shortest exact decimal. If the quantity has no finite decimal, it is `n/d` in lowest terms. The unit equals the `unit` of the type. The stored integer is the number times `factor` times `10^scale`. A reader refuses the value when it is not a whole number. Bounds are checked on the number.
- **Money.** The currency is the ISO 4217 code of the type, or the one Unicode currency sign that names only that code. A sign shared by several currencies (`$`, a yen sign, `kr`) is not a literal of any of them. The amount has exactly `scale` decimals. The `per` unit equals the `per` of the type, and is absent when the type has none. A negative zero is refused. The payload is the amount times `10^scale`. A writer that restores a literal from a payload writes the ISO code, never a sign (Q18).
- **Period.** The separator is `..` for `closed` and `..<` for `half_open`. Both ends are values of the `over` type, as text, and the first is not after the second. For an `Integer` end, the ends are text inside the period, whatever the integer's own spelling.
- **Enum.** A closed enumeration accepts its listed values. An open enumeration accepts any text. The reader does not check it.
- **Imported types.** A value of a type that comes from an imported pack cannot be checked without that pack's schema. A reader refuses it, and does not read it as text (Q19).

A float is never read. A boolean in a place of a non-Bool type is refused. A string in place of a number, or a number in place of a string, is refused.

A many-valued slot is a JSON array of values, or a state object. Its members are distinct, by payload. An array with a duplicate member is refused. The members have no order. A `+` slot has at least one member.

### 3.3 States

Every value of a slot is in one of four states, in code order: `known`, `not_applicable`, `unknown` and `invalid`.

A known value is a value of its type. The other three are written as one-member objects.

| State | Row JSON |
|---|---|
| `not_applicable` | `{"$na": "<reason>"}` |
| `unknown` | `{"$unknown": "<reason>"}` |
| `invalid` | `{"$invalid": "<reason>"}` |

The member value is a reason (section 2.3). It is text, empty if no reason is stated.

- A state object has exactly one member.
- A state not in the slot's `states` is refused.
- A writer MUST write the state of an absent value. A row that leaves out a slot is refused. Absence is never implied.
- A state may stand for a whole many-valued slot if the slot allows it. An empty array `[]` is a known empty set. It is not a state.
- A closed, optional, many-valued slot over a relation that is not read in full has no way to say "none". The publisher writes such a slot as `world: open`, and writes `unknown` for each element without a readable value. The reason it writes is `not_read_in_full`.

A state is part of the hash (section 6.2) as `{"$state": "<state>", "$reason": "<reason>"}`.

### 3.4 References and IRIs

A reference is the object `{"$ref": "<id>"}`. It has no other member. The id is non-empty text.

For a kind of the same pack, `<id>` is the id of the target element.

For a kind of an imported pack, `<id>` is `<pack>@<schema id>[@<manifest id>]@<dataset hash>:<Kind>/<id>`. A reader checks that:

- `pack` and `schema` equal those of the import;
- `Kind` is the kind the slot names;
- the dataset hash equals the import's `dataset`, and the manifest id equals the import's `manifest`;
- an epoch pin without a hash pin is refused.

The payload is the target id. The pins live in the import, so the payload does not repeat them.

A slot with `inverse` is not written.

An element has one IRI: `<kind iri>/<spelled id>`. The `<kind iri>` is the `iri` of the root of its kind tree, or `<base><Root>` if it has none. A `map` entry never names an element space.

An id is spelled as one IRI segment.

- The letters A-Z and a-z, the digits, and the characters `-`, `.` and `_` stay as they are.
- Every other character, and also `~`, is written as `~` followed by two upper-case hex digits, once per byte of its UTF-8 form.
- The ids `.` and `..` are written `~2E` and `~2E~2E`, since a client removes a dot segment before it sends the request.

An IRI reads back to one id. A segment that is not the spelling of its id is refused. A `~` not followed by two upper-case hex digits is refused.

The slot IRI is `<kind iri>#<slot>`, or the `map` entry, taken on the kind that declares the slot.

### 3.5 `$why` and `$src`

`$why` and `$src` are annotations. They explain a row. They do not change a value.

`$why` is an object. Its keys are slot names, or `$id`. A key that is neither is refused.

- For a single-valued slot, or `$id`, the value is a proof URI.
- For a many-valued slot, the value is an object that maps the payload of a member to a proof URI. The payload is the text itself, or its canonical JSON when it is not text.
- A proof URI is an absolute IRI. An opaque URI is accepted, for example `rezono:w/<hash>` for a witness.

`$src` is an object. Its keys are slot names, or `$id`. Each value is a non-empty array of Source objects.

- The array holds distinct objects and is sorted by their canonical JSON.
- A Source has these members, all text: `kind`, `name`, `revision`, `position`, `url`, `retrieved_at`, `fragment_sha256`, `ownership`, `licence`, `attribution`. Any other member is refused.
- `kind`, `name` and `position` are required. `kind` is one of `git`, `pack`, `scenario`, `proposal`, `query`, `tool`, `person`, `document` and `synthetic`.
- A `git` or `proposal` Source has a `revision`.
- A `revision` that is a manifest, `m-<epoch>`, carries its hash pin, `m-<epoch>@d-<64 hex>`.
- `url` is an absolute HTTP or HTTPS URL.
- `retrieved_at` is a UTC instant.
- `fragment_sha256` is 64 hex digits.
- `ownership` is `first_party` or `third_party`. A third-party Source has `licence` and `attribution`.
- A `document` Source has `url`, `fragment_sha256`, `licence` and `attribution`, a trimmed `position`, and a `revision` or `retrieved_at`.
- `licence` and `attribution` are trimmed text.

A reader checks the shape only. What a role may read of `$why` and `$src` is the publisher's decision. The hash keeps both outside the dataset hash (section 6.3).

### 3.6 Versioned kinds

A kind is versioned when it has `versioned`. It lists axes, with at least one of `at`, `during`, `in` and `known`.

- `at` is `Date` or `DateTime`.
- `known` is `Date` or `DateTime`.
- `during` and `in` name a kind of the schema, or of an import.

`applies` MAY map an axis to a slot of the kind. For `at` the slot is a `Date` or `DateTime`. For `during` and `in` the slot is a reference to the kind the axis names. A kind with `applies` is versioned.

A row of a versioned kind MAY carry `$valid`. It is an object keyed by axis. An empty `$valid` is refused: leave it out.

- `at` is a half-open range `a..<b`, or an open range `a..`. A closed range `a..b` is refused. `..<` without an end is refused. An empty range is refused. `a` and `b` are in the form of the axis type.
- `during` is a stage `s1`, a half-open stage range `s1..<s3`, or an open range `s1..`. A closed range is refused. There is a first stage.
- `in` is a non-empty list of setup ids. The list is distinct and in hash order (sorted by the UTF-8 bytes of the canonical JSON of each entry).
- An axis the kind does not declare is refused.

A row of a kind that declares `known` MUST have `$known`, a date or time of the axis type. A row of a kind that does not declare it MUST NOT. A row of a kind that is not versioned MUST NOT have `$valid` or `$known`.

The key of a versioned row is `($kind, $id, CJ($valid), $known)`. Several rows of one element are different versions.

A derived slot MAY list `versions`, the definition versions of the slot. It is a non-empty list of objects `{"version", "valid", "known"}`.

- `version` is a natural number as text. It is higher than the one before.
- `valid` is a `$valid` object.
- `known` is a date or time.

Only a derived slot lists `versions`.

A versioned kind has no RDF form yet (Q13).

### 3.7 Control kinds and admission

A schema separates two planes. The data plane holds facts. The control plane holds decided values: values that a review has set. A control kind carries the marker `plane`.

- `plane` is the text `control` only. A data-plane kind leaves it out. `plane: data` is refused.
- A control kind declares `owner`, non-empty text. A kind that is not a control kind does not.
- A control kind has a slot `decision`, with `card` `1` and states `["known"]`. Its type is `Text`, or it is a reference.

`plane` and `owner` are part of the schema, so they are part of the schema id (O13).

**Admission** is the one check that every delta passes. A delta is a list of rows. The reader is the same for a batch, for a service and for a party outside Rezono (LS0).

1. The schema is checked. Admission never trusts a schema.
2. The delta is read as a dataset (section 3.1).
3. For each row of a control kind, the reader asks a `reviewed` function with the `decision`. If the `decision` is a reference, it asks about the id the reference names, not about the text of `$ref`. The function MUST return the boolean `True`. A `decision` that is empty names no review, and the row is refused.
4. A row of a data-plane kind needs no review.

How a review is checked belongs to the caller. L0 only requires that a control row names one.

The **definition hash** (section 6.3) covers only the tables of the control kinds. It does not change when a fact changes (O14).

## 4. The columnar form

The columnar form is the dataset as Apache Arrow tables, written as Arrow IPC files or Apache Parquet files. A writer reads the rows first, so it writes only valid output.

Floating-point types MUST NOT occur. Exact values use integers and decimals.

### 4.1 Tables

A dataset has these tables.

- One **kind table** per kind, named by the kind name. A subkind has a table of its own. An element of a subkind is one row of the subkind's table.
- One **relation table** per many-valued slot without `inverse`, named `<Kind>__<slot>`.
- Two **side tables**, `$why` and `$src`.

The empty tables are present too.

A kind table has these columns, in this order.

1. `$id`, with the element id.
2. For a versioned kind: `$valid`, the canonical JSON of the `$valid` object as text (`{}` if there is none); and `$known` if the kind declares `known`.
3. For each slot without `inverse`, in slot-name order, as the schema id reads them: the value column, then the state columns (section 4.3).

A many-valued slot has no value column in the kind table. Its members are in its relation table. A many-valued slot with more than `known` in its states still has the two state columns.

A relation table has `$id`, the version columns of the owner kind, and the member column, named by the slot. There is one row per member.

A side table has these columns, all text.

| Table | Columns |
|---|---|
| `$why` | `kind`, `id`, `slot`, `member`, `proof`, and `valid`, `known` if any kind is versioned |
| `$src` | `kind`, `id`, `slot`, `member`, `source`, and `valid`, `known` if any kind is versioned |

`member` is null for a single-valued slot. `valid` and `known` are null for a kind that is not versioned. `source` is the canonical JSON of the Source.

The rows of every table are in hash order (section 6.2, step 3), and the members of a relation in hash order. A reader MUST NOT depend on the order. A writer MUST write it, so a round trip is byte-equal in canonical JSON.

A reader takes everything from the schema document and the column names. It rejects a table that disagrees with the schema.

### 4.2 Metadata

The Arrow schema of every table carries a metadata entry `rezono`. Its value is the canonical JSON of an object. In Parquet, the file's key-value metadata carries `rezono` as well. It does so even when `ARROW:schema` is not stored.

The members are these.

| Member | Required | Meaning |
|---|---|---|
| `rezono` | yes | `"1.0"` |
| `schema` | yes | the schema id |
| `table` | yes | the table name |
| `role` | yes | `kind`, `relation`, `why` or `src` |
| `plane` | for control tables | the text `control` |
| `dataset` | no | the dataset hash `d-…` the table belongs to |
| `manifest` | no | the manifest id |
| `table_hash` | no | the table hash, 64 hex digits (section 6.2, step 4) |

Any other member is refused. Rules:

- `schema` equals the id of the schema read under.
- `table` is a kind table when `role` is `kind`, and a relation table (`<Kind>__<slot>`, with a many-valued slot, no `inverse`) when `role` is `relation`.
- A side table is named `$why` or `$src`, with the role of the same name, and has no `plane`.
- `plane` is present exactly for the table of a control kind.
- `manifest` without `dataset` is refused: an epoch pin needs its hash pin.
- `dataset` is a full dataset hash. `manifest` is a manifest id.

Every field carries a `rezono` metadata entry too. Its members are `slot`, `role` (`id`, `valid`, `known`, `value`, `member`, `owner`, `state`, `reason`), `type`, and `ref` for a reference. A file without field metadata (Parquet written without `ARROW:schema`) reads the same, because a reader takes everything from the schema.

### 4.3 States as columns

A slot that allows a state other than `known` has two columns beside its value column.

- `<slot>$state`, an `int8` with the state code: 0 `known`, 1 `not_applicable`, 2 `unknown`, 3 `invalid`.
- `<slot>$reason`, text. It is `""` for state 0.

The value column of a slot with these columns is nullable. It is null exactly when the state code is not 0. A value beside a state, and a null beside state 0, are refused. A reason beside state 0 is refused. A state code that is not 0 to 3 is refused.

A slot whose states are `["known"]` has a value column that is not nullable, and no state columns.

### 4.4 Storage

The storage of a slot's value column follows from its type, in this table. An Arrow type is written without spaces.

| Type | Storage |
|---|---|
| a reference | `utf8` |
| `Text`, `Enum`, an imported type | `utf8` |
| `Bool` | `bool` |
| `Date` | `date32` |
| `DateTime` | `timestamp(us,"UTC")` |
| `Integer` | see below |
| `Ratio` | `struct<numerator:decimal128(38,0),denominator:decimal128(38,0)>` |
| `Quantity` | `int64` or `decimal128(38,0)` |
| `Money` | `decimal128(38,<scale>)` |
| `Period` | `struct<from:<T>,to:<T>>`, with `T` the storage of the `over` type |

An `Integer` is stored as `int64` if `min` and `max` are declared and within the `int64` range. It is `decimal128(38,0)` if both are declared and within plus or minus (10^38 - 1). Otherwise it is `utf8`.

A `Quantity` is stored as `int64` if both bounds are declared and the stored integers (bounds times `factor` times `10^scale`) fit in `int64`. Otherwise it is `decimal128(38,0)`.

A type's `storage` member overrides these rules. A schema MAY name an Arrow type that way.

The stored value is the payload of section 3.2: for a quantity, the stored integer, and for money, the amount times `10^scale` held as a decimal of that scale. The writer holds decimals as exact decimals, never as floats.

A reader MUST reject a column whose storage differs from the one the schema gives. A dictionary of `utf8` counts as `utf8`. A decimal column with the right scale and a precision of at most 38 is accepted, except that a scale 0 column MUST have precision 38. A floating-point type is always refused.

### 4.5 Extension types

A column of a `Quantity`, a `Money` or a reference carries an Arrow extension type. Its name and metadata restate the schema exactly.

| Column | Extension name | Metadata |
|---|---|---|
| `Quantity` | `rezono.quantity` | `type`, `unit`, `storage_unit`, `factor`, `scale` |
| `Money` | `rezono.money` | `type`, `currency`, `scale`, and `per` if the type has one |
| a reference | `rezono.ref` | `kind`, and for an imported kind `pack`, `schema`, and the `manifest` and `dataset` pins of the import |

`factor` defaults to `"1"` and `scale` to `"0"`. The metadata is a JSON object. A reader compares each member with the schema's, and refuses any that is missing, extra or different. A column that takes no extension MUST NOT carry one. A column that takes one MUST carry it.

Readers that do not know the extensions read the storage values as written.

### 4.6 One file per table

A table is written as one file, in the form Arrow IPC (`arrow`) or Parquet (`parquet`).

The file name is `table.<name>.<form>`. In `<name>`, every `$` is written `_`. So `$why` becomes `table._why.arrow`.

- A Parquet file is compressed with zstd and embeds `ARROW:schema`.
- The same table gives the same bytes again, with the same writer.

A writer MUST check that two tables never give one file name. A reader of a dataset in one form MUST find a file for every table. A missing file is refused.

## 5. The RDF view

The RDF view is the full dataset as an RDF graph. It is written as RDF 1.1 Turtle or as JSON-LD 1.1. The view loses nothing: rows go to RDF and back.

A schema publishes these documents beside its id, at `<base>s-<hex>/`.

| Document | Name |
|---|---|
| the JSON-LD context | `context.jsonld` |
| the SHACL shapes | `shapes.ttl` |

Documents under `<base>s-<hex>/` are immutable, because the schema id names them.

### 5.1 The published context

The published context is a JSON-LD 1.1 context. It is protected. It has a type-scoped context for each kind. A slot name used on two kinds expands to two IRIs, one per kind.

| Term | Meaning |
|---|---|
| `$id`, `$ref` | `@id` |
| `$kind` | `@type` |
| `$rows` | `@graph` |
| `$unknown`, `$na`, `$invalid` | `rd:unknown`, `rd:notApplicable`, `rd:invalid` |
| `$valid`, `$known` | `rd:valid`, `rd:known` |
| `$schema`, `$why`, `$src` | no term |
| a kind name | the kind IRI, with a scoped context for its slots |

In a scoped context a slot name has the slot IRI. Its `@type` is `@id` for a reference, or the datatype IRI of its type.

`rd:` is the namespace of the publication profile, `<ns>/publication/1.0#`. The value of `<ns>` is open (Q1). The reference implementation uses `https://rezono.org/publication/1.0#`. A profile IRI is an identifier. It is not a fetch target.

A document names the context by its URL. A reader resolves that URL itself and never fetches it. An embedded context that redefines a term of the published one is an error (a protected term redefinition). A remote context other than the published one is refused. An embedded context may not set an `@`-keyword that changes how protected terms read.

### 5.2 The converter

The converter writes rows as triples and reads them back.

- An element is the IRI of section 3.4. It has an `rdf:type` of the kind IRI.
- A subkind has `rdfs:subClassOf` its parent.
- A closed kind has the triple `<kind> rd:world rd:closed`.
- A known value is a literal. Its datatype is the XSD type for `Text`, `Bool`, `Integer`, `Date` and `DateTime`, and a type IRI under `<base>s-<hex>/types/` for every other type. The lexical form is the Row JSON text of the value.
- A reference is an IRI of the target element.
- A state is a blank node, the object of the slot's predicate. It has one property, `rd:unknown`, `rd:notApplicable` or `rd:invalid`, with the reason as a literal.
- A many-valued slot is one triple per member. An empty set is the single triple with the object `rd:emptySet`.
- `$why` and `$src` are annotations of a statement. A statement annotation is an `rdf:Statement` with `rd:why` (a proof IRI) or `rd:source` (an `rdf:JSON` literal of the canonical JSON of the Source). RDF 1.2 triple terms are the later form of this. They are not used while the toolchain lacks them.

A reader of the view reads literals as written. It does not normalise their lexical form, and it holds it to the normal form of its type. A state that is not a blank node with one of the three terms is refused. A set that mixes members, `rd:emptySet` or a state is refused.

The blank nodes are labelled by what they stand for. The same rows give the same Turtle bytes.

A versioned kind has no RDF form yet (Q13). A reference into another pack has no IRI, because the import does not carry the other pack's `base` (Q20). A converter refuses both and never guesses.

### 5.3 Shapes

The SHACL shapes of a schema are published at `<base>s-<hex>/shapes.ttl`. They validate the RDF view of a dataset under that schema. What a validator accepts is what a reader accepts, as far as a shape can say it. What a shape cannot say is in `shacl.losses.yaml`.

- Each kind has a node shape. It is closed and has one property shape per slot.
- A single-valued slot has exactly one object: a value, or a state the slot lists.
- A many-valued slot is its members, or `rd:emptySet` alone (not for `+`), or one state. It is never a mix.
- A value is a literal of the datatype of the slot. The shape adds what SHACL can say: the pattern of a text type, the members of a closed enumeration, the bounds of an integer, the unit of a quantity.
- A reference is an IRI in the element space of the target kind.
- A state's reason is empty, or a reason code that the schema allows for that state.

The shapes refuse what has no RDF form yet, as the converter does.

#### 5.3.1 Constraints in SPARQL

A constraint that SHACL cannot write as a property shape MAY be written as a SPARQL-based constraint. Such a constraint follows the SHACL rules on SPARQL: it holds no `MINUS`, `VALUES` or `SERVICE`. The section number 5.3.1 is also that of the W3C SHACL recommendation on this limit. The repository's citations of "SHACL section 5.3.1" are about that recommendation, and this subsection only points to it. How far a pack's checks can be written this way is open.

### 5.4 PROV-O

A witness of a derived row has an RDF form in PROV-O. The graph is named by its epoch.

| Witness part | PROV-O |
|---|---|
| the conclusion row | a `prov:Entity` |
| the rule application | a `prov:Activity` |
| a premise | `prov:used` |
| the epoch | a `prov:Bundle` |

The IRIs are `rezono:w/<H(witness)>` for a witness, `rezono:r/<relation>/<key>` for a row, and `rezono:m/m-<epoch>@d-<64 hex>` for an epoch. The relation and the key are spelled as an id is (section 3.4).

PROV-O has no term for some parts of a witness. They travel as `rd:` terms: `rd:absent` for a negative premise, `rd:polarity`, `rd:stratum` and `rd:position` on each usage, `rd:rule`, `rd:binding`, and `rd:aggregate`. The witness is recovered from the graph without loss.

## 6. Hashes

### 6.1 The canonical hash

Every hash in this format is `H`, the SHA-256 digest of canonical JSON (section 1). The format hashes no bytes of its own. The logical hash of a dataset does not depend on the form it was read from: Row JSON, columnar or RDF.

A hash is computed for a dataset that a reader accepted. The computation checks only what it needs: a known state, a whole stored integer for `Quantity` and `Money`, no `null`, and no two hash rows with one key.

`H([])` is the hash of an empty table.

### 6.2 The logical hash

The logical hash of a dataset is computed in these steps.

**Step 1: the key.** For each row, the key is `[$id, ...version]`. For a kind that is not versioned, `version` is empty. For a versioned kind it is `[CJ($valid), known]`, with `{}` for a missing `$valid`, and `""` if the kind has no `known`.

**Step 2: the hash row.** For a kind table, the hash row is the object `{"$key": key}` with one member per slot without `inverse` and not many-valued.

- A known value is its payload (section 3.2). For example, a quantity of 400 GiB is its stored integer `"429496729600"`. An `Integer` is its text, so `42` and `"42"` hash alike.
- A state is `{"$state": "<state>", "$reason": "<reason>"}`.
- A reference into another pack is the target id without the pack prefix.
- A many-valued slot in a state is the state object in the kind table.

For a relation table, there is one hash row per member: `{"$key": [$id, ...version, m]}`, with `m` the payload text, or its canonical JSON when it is not text. So the member `4` of a bounded integer keys as `"4"`.

**Step 3: the order.** The hash rows of a table are sorted by the UTF-8 bytes of `CJ($key)`. Two rows with the same key are an error. For example, `["a b"]` sorts before `["a"]`, which sorts before `["a-b"]`.

**Step 4: the table hash.** The hash of a table is `H([row, ...])` over the hash rows in hash order. An empty table has the hash `H([])`.

**Step 5: the dataset hash.** The dataset hash is `"d-" + H({"schema": <schema id>, "tables": {<table>: <table hash>}})`. The tables are the kind tables and the relation tables, all of them, empty ones too. The side tables are not in it.

**Step 6: the side tables.** There is a hash row for each row of `$why` and `$src`. Their keys have six or seven parts.

- `$why`: `{"$key": [kind, id, slot, member, valid, known], "proof": <uri>}`. `member` is `""` for a single-valued slot. `valid` and `known` are `""` for a kind that is not versioned.
- `$src`: `{"$key": [kind, id, slot, "", valid, known, CJ(source)]}`. There is one row per Source.

The side tables are sorted and hashed as in steps 3 and 4. They are outside the dataset hash.

A hash does not normalise Unicode. An id in two Unicode forms is two ids. The order of rows, and of members, in the input does not change the hash.

A worked vector is given by the case `H06` (section 8): the fixture schema and two rows.

### 6.3 Annotation and definition hashes

The **annotation hash** covers the side tables: `H({"dataset": <dataset hash>, "tables": {"$src": <$src table hash>, "$why": <$why table hash>}})`. A change of `$why` or `$src` changes the annotation hash and leaves the dataset hash as it is.

The **definition hash** is `"c-" + H({"schema": <schema id>, "tables": {...}})`. The tables are only those of the control kinds (section 3.7), kind tables and relation tables, empty ones too. It does not change when a fact changes.

A publication MAY add a row tree over each table, so a verifier can check that a row is in a dataset (an inclusion proof). The tree is a Merkle tree as in RFC 9162: a leaf is `SHA-256(0x00 || CJ(row))`, a node is `SHA-256(0x01 || left || right)`, and an empty table has the root `SHA-256()`. The dataset hash is not changed by it. The statement that carries the roots is outside L0.

### 6.4 Pins

A **pin** names an epoch of a pack and its content. There are two pins.

- The **epoch pin** is the manifest id `m-<epoch>`.
- The **hash pin** is the dataset hash `d-<64 hex>`.

An epoch pin MUST come with its hash pin. A manifest id alone is refused. The refusal is the same wherever a pin occurs: in an import, in a reference into another pack, in the metadata of a table, and in the `revision` of a Source.

The full pin of a dataset, in this order, is `<pack>@<schema id>@<manifest id>@<dataset hash>`. The manifest id is the one that may be left out, so the forms `<pack>@s-…@d-…` and `<pack>@s-…@m-…@d-…` are both full pins. A schema id is always given in full.

## 7. Forms and media types

A publication is available in the forms below. A form is a representation of the same dataset. All forms carry the same facts.

| Form | Media type | Normative source |
|---|---|---|
| Row JSON | `application/json` | RFC 8259 |
| JSON-LD | `application/ld+json` | W3C JSON-LD 1.1 Recommendation |
| Turtle | `text/turtle` | W3C RDF 1.1 Turtle Recommendation |
| Parquet | `application/vnd.apache.parquet` | IANA media type registration for Apache Parquet |

Apache Arrow IPC files are the second columnar form (section 4.6). This document names no media type for them.

A server that offers a form uses the media type of its row in this table. A publisher MAY write a form only when the dataset has it: for example, a schema that has a versioned kind, or a reference into another pack, has no Turtle or JSON-LD form yet (section 5.2).

The publication profile is the IRI `<ns>/publication/1.0`, under the namespace of `rd:` (section 5.1). `<ns>` is open (Q1). A row JSON document, the context, the shapes and the data contract each hold to the profile and to the schema they sit beside.

A **delta profile** is a profile of row JSON that a writer may use for a delta before admission. The reference reader does not read it. Its content is open.

### 7.1 A dataset with its schema

An answer to a question about a dataset MAY be a publication dataset. It is an object with three members.

- `$schema` is the schema id of the answer's own schema.
- `schema` is that schema document.
- `rows` is the list of rows, in Row JSON.

`$schema` equals `H` of `schema`. The schema is a schema document of section 2. The caller of an answer reads its types from it. It need not guess them.

The answer schema has two kinds, `Answer` and `Undecided`.

- `Answer` has a slot `binder` and one slot `c1`, `c2` and so on for each value the question shows. Each such slot has the type that the question gives, the states that the typing allows, and the printed expression as `expr`.
- `Undecided` has the slots `binder`, `state`, `reason`, `cause_relation` and `cause_key`. `state` is `unknown` or `invalid`.
- Both kinds are closed.
- The types and kinds of the pack it asks about are used through an import with the prefix `p`, which pins the pack's schema id.
- The `base` of the answer schema is under the base of the pack's schema, with the hash of the question in the path.

The names are fixed, so no name in a question can collide with them. The rows of a page are the `Answer` rows, then the `Undecided` rows.

The same dataset hash MUST come out for two worlds that a role cannot tell apart (case Y03, pending). How an answer request treats a missing or stale access epoch, and with what status, is open (Q15).

## 8. Conformance cases

The cases are the conformance suite of this format. They are YAML files in `docs/publication/cases/`, one per case, with a JSON Schema in `schema.json`. The fixture schema document is `fixture.schema.json`.

A case has these members.

| Member | Meaning |
|---|---|
| `id` | a letter and two digits, for example `R01` |
| `class` | `valid`, `invalid`, `change`, `hash`, `context`, `admission`, `oracle`, `round-trip`, `answer` or `subscribe` |
| `status` | `settled`, `pending` or `open` |
| `schema` | `from` the fixture, with an optional `merge` |
| `successor` | for a `change` case, a `merge` that gives schema B |
| `form` | what `input` is: `schema`, `schema-text`, `row`, `rows`, `collection`, `datasets`, `json-text`, `jsonl`, `jsonld`, `arrow-field`, `parquet`, `parquet-metadata`, `delta`, `answer`, `request` or `events` |
| `input` | the input |
| `expect` | what a reader or a verifier must do |
| `note`, `sources` | explanation, and where it comes from |

A `merge` is an RFC 7396 JSON merge patch. It is applied to the fixture schema (or to schema A), so a case states only the difference.

A case `status` of `settled` means the format fixes the outcome. A `pending` case needs something the format's own reference code does not run, for example an endpoint. An `open` case waits for a decision.

`expect` has one or more of: `accept`, `error` (a fragment of the error text), `schema_id`, `dataset_hash`, `annotation_hash`, `side_tables`, `change_class`, `read_old_rows`, `same_rows_as`, `same_definition_hash`, `same_dataset_hash`, `versions`, `hash_keys`, `payload`, `arrow_ref_metadata`, `iris`, `expanded`, and others for the pending cases.

The case id letter groups the cases.

| Letter | Subject | Sections |
|---|---|---|
| `A` | columnar fields and files | 4.4, 4.5 |
| `G` | control kinds and admission | 3.7 |
| `H` | hashes | 6.2 |
| `M` | change classes | 2.4 |
| `N` | reasons | 2.3 |
| `P` | pins and imports | 3.4, 4.2, 6.4 |
| `R` | rows and collections | 3 |
| `S` | schema documents | 2 |
| `V` | versioned kinds | 3.6 |
| `X` | the RDF context and IRIs | 3.4, 5 |
| `Y` | answers and subscriptions | 7.1 |

The fixture schema has the pack `fixture` and the base `https://rezono.example/fixture/`. It has two kinds. `Host` has `memory_need` (a `GiB` quantity, `1` card, states `known` and `unknown`), `owner` (a reference to `Team`, `?`, states `known`, `not_applicable`, `unknown`) and `tags` (text, `*`, only `known`). `Team` has no slots. The fixture is accepted and has a fixed schema id (case S01). Its id does not change when the members are reordered or white space is added (case S02).

A reader or verifier is conformant when it gives the outcome of each settled case. A reader that rejects a valid case, or accepts an invalid one, is not.

## Open questions

The code and the cases refer to these questions by number. Each entry says what the code does today.

**Q1: the namespace of the profile.** The profile IRI is `<ns>/publication/1.0#`. `<ns>` is not fixed. The code uses `https://rezono.org/publication/1.0#` as the namespace `rd:`, and treats the profile IRI as an identifier, not as something to fetch.

**Q7: omitted members.** A row that omits a slot is invalid. The code refuses it. A writer MUST write the state of an absent value (section 3.3). No code gives an omitted member a meaning.

**Q12: ODCS version and mapping.** The data contract (section 2.5) names one ODCS version, `v3.2.0`, in one constant. Which version and which field mapping Rezono settles on is open.

**Q13: versioned kinds in RDF.** How a versioned element maps to RDF nodes is open. The converter and the shapes refuse a versioned kind with an error that names Q13. A connector may leave out its export for this reason, with a note. It never guesses.

**Q15: the status of a refused answer request.** An answer request without an access epoch, or with a stale one, is refused (case Y02). The status code of the refusal is open. No code decides it.

**Q18: money symbols.** The schema names no currency symbol. A reader accepts the ISO 4217 code, or the one sign that names only that code (for example the euro sign). A sign shared by several currencies is refused. A writer that restores a literal from a payload writes the ISO code, so `€ 12.30` comes back as `EUR 12.30`. The payload and the hash are the same.

**Q19: imported types.** A value of a type from an imported pack cannot be checked without that pack's schema, and a reader does not hold it. A reader refuses such a value with an error that names Q19. It does not read it as text. How a reader gets and checks the imported schema is open.

**Q20: references into another pack in RDF.** The IRI of such a target needs the other pack's `base`. The import does not carry it. The converter and the shapes refuse the reference, with an error that names Q20.

**Q22: two slots, one type, two patterns.** A publisher names a type after the schema type of a slot. If two slots have the same schema type but different inline patterns, they would share one type. The publisher refuses to write such a form. How to write it is open. The bounds of an integer type are still those of the last slot.
