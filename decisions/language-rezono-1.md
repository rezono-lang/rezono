# Rezono 1: one derivation form as the first released language

`rezono 1` is the language of the first public release, with **one derivation form** (`derived`). `rezono 0` remains the internal workbench and keeps its existing syntax, semantics, and canonical printed form unchanged ([language reference §4b](../docs/rezono/v0.md#4b-language-version-and-deprecation)). Existing pack rule files convert **once**, directly from `.dl` or embedded `rules` blocks to `rezono 1`, rather than twice through `rezono 0` native rules.

This decision adopts and finalizes the design explored in [the first-release proposal](../docs/rezono/first-release-proposal.md), resolves every technical correction and open gap against the codebase, settles the effect on prior language decisions, and specifies every intended semantic difference for migrating `examples/platform/rules/core.dl`.

> **Follow-up refinements ([`decisions/language-rezono-1-refinements.md`](language-rezono-1-refinements.md)):** prohibits implicit existential variables in relation calls (adding optional explicit binders `Kind.any(x: ...)` / `rel.any(row: ...)`), introduces `a otherwise b` for conflict-safe fallback on `n/a` plus `W115` on `unless x is known`, enforces set-only collections (`R028` on collection path projection, plus `.one(expr)`), aligns `.count(pred)` and `x in S`, replaces alphabetical `round` type selection with `round(x as Type, mode)` / `default_units`, and unifies the symmetric 64-bit exact-number bound (`BOUND = 2^63 - 1`) and all four rounding modes across engines.

## 1. Fixed invariants and scope

Four constraints hold for every part of `rezono 1`:

- **Feldera remains the target incremental engine**, alongside DuckDB for batch/publication and Soufflé as an independent test oracle for the non-rational fragment.
- **Every program terminates.** Unbounded recursion, general arithmetic inside recursion (beyond the existing bounded-counter profile), and `min` or `max` inside recursion remain refused.
- **No built-in `best` or `first` over sets.** Choosing a winner over a set must remain explicit in the pack's candidate inventory, exclusions, and tie policy. (Static row-order `table first` remains explicit in the authored text.)
- **Symbols remain symbols.** `?`, `*`, `+`, `..<`, `@`, `-`, and `_` keep their symbolic form with no keyword synonyms introduced beside them.

## 2. One derivation form (`derived`)

Every derivation in `rezono 1` uses `derived`:

- **Key placement and bundle naming:**
  - **One kind key** -> derived property inside `kind K` or `extend K` (or `extend s: K` when naming the subject binder). In `ir/rules.json`, engine SQL views, `bundle/schema-bundle.json` (`DerivedRelation.id`), and `labels/<lang>.yaml`, a derived property `d` on kind `K` (snake_case kind id `k`) has the canonical relation name **`<k>_<d>`** (single underscore, matching [`docs/rezono/publication.md`](../docs/rezono/publication.md#54-a-derived-truth-value) §5.4 and §9.1, [`decisions/language-tables.md`](language-tables.md), and `compiler/rezono_compiler/rezono_table.py`; e.g. `Service.zone` -> `service_zone`, `Product.newest_day` -> `product_newest_day`, `Service.behind_newest` -> `service_behind_newest`). Stored slots continue to use double underscore (`<k>__<slot>`). `DerivedRelation` in [`contracts/bundle.yaml`](../contracts/bundle.yaml) carries `kind: "<k>"` and `property: "<d>"` alongside `id: "<k>_<d>"` so viewers and L0 publishers map it back to `K.d`. Collisions between `<k>_<d>` and any other relation or table name are rejected by `emit.namespace()`.
  - **Two or more keys** -> module-level `derived name(k1: T1, k2: T2, ...): R`, which enters the IR and bundle under its declared `name`. No artificial wrapper kind is ever invented for n-ary relations.
- **Result types and semantics:**
  - **`Bool`:** plain set relation. Every succeeding derivation keeps its own independent proof; stratified positive recursion is permitted; no extra state or reason columns are added.
  - **`T*`:** set-valued derivation yielding every derived member for a key (no uniqueness conflict; positive recursion permitted).
  - **`T` or `T?` (functional value with state):** for every key in its declared finite closed domain:
    - exactly one distinct value yields `known(v)` with its witness;
    - two or more distinct values yield `invalid` with a reason code and **every candidate value and its proof as witness** (never a silent pick);
    - zero values from `.one()` (`|S| = 0`) yield **`unknown no_match`** when the declared type is `T` and **`not_applicable no_match`** (`n/a`) when the declared type is `T?`;
    - on any non-`total` functional derivation (`T` or `T?`), **`not_applicable` (`n/a`)** also propagates directly from the body expression whenever `.min(...)` or `.max(...)` evaluates over an empty set (`not_applicable empty`, per [`docs/rezono/expressions.md`](../docs/rezono/expressions.md#appendix-a-truth-tables-normative) Appendix A.3), a path reads an absent optional slot (`not_applicable no_value`), an explicit `n/a` literal is returned, or a `when` guard evaluates to `n/a` (`expressions.md` Appendix A.2);
    - missing required inputs or unmatched rules/versions yield `unknown` with the corresponding reason code (`no_value` for a missing required slot or undecided table row, `no_row_applies` when no table row applies, `no_version_applies` when no version applies).
- **Mandatory finite closed domain (`over`):**
  - Every functional derivation in `rezono 1` MUST have a **finite, closed** domain `D` (`world: closed`).
  - Single-key functional derivations on `kind K` / `extend K` use `K` as their domain and require `K` to have `world closed`.
  - Multi-key functional derivations MUST declare a finite base or strictly lower-stratum `Bool` domain relation via `over D(k1, ..., kn)` where `D` has `world: closed`. A Cartesian product of kinds (such as `Service × Function`) and any `open` domain kind or relation are rejected at compile time (`functional_open_domain` in `rezono.rules/2`), preventing both unbounded incremental state materialization and unsound totalization over open worlds.
- **Set-to-functional conversion (`.one()`):**
  - `S.one()` over a closed set `S: T*` yields:
    - `known(v)` when `|S| = 1` (witnessed by the single member plus `count = 1` and `contributors_sha256`);
    - **`unknown no_match`** (when the declared type is `T`) or **`not_applicable no_match`** (when the declared type is `T?`) when `|S| = 0`;
    - **`invalid multiple_values`** carrying every distinct member and its proof as conflict witness when `|S| > 1`.
- **Uniform modifiers and core reason codes:**
  - Ordered and sibling `unless` blocks, `version` blocks (`valid`, `known`, `replaces`), `table` blocks (`unique`, `first`, `collect`), `means "..."`, and `@ source#locator` work uniformly on `derived` declarations.
  - Existing core reason codes in [`contracts/value.yaml`](../contracts/value.yaml) and [`docs/publication/l0.md`](../docs/publication/l0.md#23-reasons) (`no_version_applies`, `versions_overlap`, `exception_conflict`, `no_row_applies`, `empty`, `ambiguous_date`, `added_later`) stay unchanged.
  - **`no_value` keeps its existing meaning exclusively:** a missing slot value (`docs/rezono/publication.md` §4 item 5 and §5.4: `not_applicable no_value` for an absent optional slot, `unknown no_value` for a missing required slot) or an undecided decision-table row caused by a missing required input (`compiler/rezono_compiler/rezono_table.py`, `docs/rezono/publication.md` §9.1). It is NOT overloaded for empty `.one()` candidate sets.
  - Two new core reason codes are added to [`contracts/value.yaml`](../contracts/value.yaml), [`docs/publication/l0.md`](../docs/publication/l0.md#23-reasons), and `publication/rezono_publication/l0.py` (`CORE_REASONS`):
    - **`no_match`** — allowed states: `not_applicable`, `unknown` (for `|S| = 0` in `.one()`);
    - **`multiple_values`** — allowed state: `invalid` (for `|S| > 1` in `.one()`).
- **Publication conflict policy:**
  - **Rule-structure contradictions always block publication (`conflict_policy = block`, automatic invariant):** unresolved `versions_overlap`, sibling `unless` clashes (`exception_conflict`), and overlapping `table unique` rows.
  - **Data-multiplicity conflicts from `.one()` (`invalid multiple_values`) publish as findings by default (`conflict_policy = publish`)** on `partial` derivations (the default per `v0.md` §5d): the functional derivation emits `(key..., "invalid", "multiple_values", "")` (with `value` omitted in structured `Value` JSON per `contracts/value.yaml`, `""` in snapshot row keys, and a non-NULL typed sentinel in SQL) carrying every candidate as witness; downstream `Bool` derivations reading its value (`d(k) = v`) require `state = "known"` and emit no false positive tuple; and checks or diagnostic views can test `d(k) is invalid` directly. A pack that wants data multiplicity conflicts to block publication writes `check` / `require` (e.g. `check unique_provider: not (needs(a, f) is invalid)`) or declares the derivation `total`.
- **Guarding `unless` without masking `invalid`:** because `is` always evaluates to `true` or `false` (`v0.md` §7b), an optional-override fallback in `rezono 1` uses the conflict-safe `otherwise` operator (`chosen(a, f) otherwise ...`, [refinements](language-rezono-1-refinements.md#2-conflict-safe-fallback-on-na-with-otherwise-and-warning-w115)); an `unless` guard that writes `unless not (chosen(a, f) is n/a) then chosen(a, f)` also forwards `invalid`, whereas `unless chosen(a, f) is known` would silently mask a conflict in `chosen` and triggers warning `W115`.

## 3. Effect on prior decisions

Existing `rezono 0` decisions stay in force for `rezono 0` modules and packs, and each referenced decision now links forward to this decision. For `rezono 1`, this decision supersedes, narrows, or extends five prior decisions as follows:

1. **[`decisions/language-native-rules.md`](language-native-rules.md):**
   - Stays in force for `rezono 0` (`rule ... when ...` in `rezono.module/3`); the existing `rezono 0` native-rule chain stays green as the workbench base.
   - Superseded for `rezono 1` by unified `derived` in `rezono.module/5`. Both design objections in `language-native-rules.md` remain satisfied: multi-key derivations stay module-level declarations with explicit typed keys (no wrapper kinds) and `Bool`/`T*` derivations preserve multiple independent proofs; `Bool` derivations stay plain sets with unchanged arity and proofs, and only non-`Bool` functional derivations carry `(state, reason, value)` over their declared closed domain.
2. **[`decisions/language-tables.md`](language-tables.md):**
   - Stays in force for `rezono 0` (including `table priority` as already built and tested, with **no `W107` warning** in `rezono 0`, preserving `docs/rezono/cases/T04.yaml`, `compiler/tests/rezono/test_lower_table_policy.py`, and `rezono/test/test_rezono_1_version_switch.py`).
   - For `rezono 1`, `table unique` and `table first` lower through the co-located functional derivation IR (`rezono.rules/2`) and `table collect` lowers through set-valued `T*` derivations rather than emitting 6–11 separate Datalog relations per value; **`table priority` is refused in `rezono 1` (`R028`, hint: `table first`)**.
3. **[`decisions/language-calculations.md`](language-calculations.md):**
   - Stays in force for `rezono 0` and legacy `calc/*.yaml` files.
   - Reconciled accurately (see Section 5, item 7): in `rezono 0`, `decisions/language-calculations.md` refuses `unless`, decision tables, state tests, sets, and aggregates in `rezono.calc/1` with `R050`; [`decisions/language-exceptions.md`](language-exceptions.md) lowers ordered `unless` blocks into `rezono.calc/1` definitions with `overrides`, while decision tables lower through `compiler/rezono_compiler/rezono_table.py` into `rezono.rules/1` (never through `rezono.calc/1`).
   - For `rezono 1`, those `R050` refusals are superseded: single-subject calculations, multi-key functional derivations, `unless`, `version`, `table`, state tests, and set aggregates lower uniformly through `rezono.rules/2` (see Section 5, item 6).
4. **[`decisions/language-readable-rules.md`](language-readable-rules.md):**
   - Stays in force for the shorter module header defaults and `means` / `@` on rules; both carry forward into `rezono 1` (where redundant defaults become `R028` and `linkml:types` is always implicitly imported, as scheduled there).
   - The two candidates left open in `decisions/language-readable-rules.md` — single-key derived properties inside `kind`/`extend`, and simpler method-form filtering/counting/summing (`.where(...)`, `.count(pred)`, relation-as-tuple-set) — are **adopted** for `rezono 1`.
5. **[`decisions/language-safe-steps.md`](language-safe-steps.md):**
   - The three `rezono 0` safe-step building blocks (`insert_row` in `suppose`, `step`, `invariant intermediate within`) continue to be built in `rezono 0` (`rezono.module/4`). A `step` lowers to a valueless match relation (`CompiledStep.match_relation`), which remains a `Bool` relation in `rezono 1`.
   - Platform packs convert their steps once, together with their rules, to `rezono 1`.
   - **What a `step` in `rezono 1` may read from a value-bearing (functional) derivation `d`:**
     - **In `when`:** may read a strictly lower-stratum functional derivation `d` positively for a known value (`d(k) = v`, requiring `state = "known"` and carrying `d`'s proof into the step match witness), or test its state positively (`d(k) is known`, `is unknown`, `is n/a`, `is invalid`) under the round's observation cut (carrying the state row and its witness; every functional derivation already has a closed domain). Reading `d(k)` in a value position when its state is `unknown`, `n/a`, or `invalid` never produces a step match.
     - **In `forbid <pattern> within <scope>`:** both `<pattern>` and `<scope>` remain direct `Bool` or base relation calls (not functional derivations), because scoped absence requires a complete key inventory. To forbid a condition involving a functional value, write a lower-stratum `Bool` relation or a state test in `when`.
     - **In `effect` (record keys, slot values) and `confirm` (`reader` arguments, `token`):** every expression referencing a functional derivation `d(k)` must require `d(k)` to be `known` (either bound positively in `when` or enforced by the compiler adding `state = "known"` to the step's match relation). An `unknown`, `n/a`, or `invalid` value can never be written into an effect delta, used as a record key, or passed as a confirmation token.
     - **In `invariant intermediate within <coverage>`:** written on `derived ...: Bool` derivations in `rezono 1`; the violation derivation may read lower-stratum functional derivations (value or state) under the same closed-domain stratification rules, while `<coverage>` remains a `Bool` or base relation.

## 4. Underlying IR, witnesses, checker, and engines (`rezono.rules/2`)

Pure desugaring of `rezono 1` functional derivations into `rezono.rules/1` + `rezono.calc/1` does not suffice: `outcome` in `rezono.rules/1` is restricted to one 1-column base kind and three states (`known`, `unknown`, `not_applicable`), naive table-style Datalog desugaring multiplies views by 6–11× per value (increasing pipeline count and cross-pipeline traffic), `rezono.calc/1` is single-subject/single-phase and numeric/Boolean-only, and conflict witnesses must carry every competing candidate rather than a single pair of row numbers.

`rezono 1` therefore extends the rule IR additively as **`rezono.rules/2`** (while `rezono.rules/1` remains valid for `rezono 0`):

- **Functional relation role (`contracts/rules.yaml`):**
  - Keep `role: derived` unchanged for `Bool` and `T*` set relations.
  - Add `role: functional` carrying: `key` (1+ typed columns), `domain` (mandatory name of a `world: closed` base or strictly lower-stratum `Bool` derived relation whose key columns match `key`; an `open` domain is refused with `functional_open_domain`), `value` (one typed column: `string`, `integer`, `rational`, or `boolean`) with co-located `state` (`known`, `unknown`, `not_applicable`, `invalid`) and `reason`, `world: closed` unconditionally, `conflict_policy` (`block` for rule-structure contradictions vs `publish` for `.one()` multiplicity conflicts), and ordered precedence/version/candidate rules strictly in a higher stratum than `domain` and outside any recursive component. Single-key derived properties use relation id `<k>_<d>` (Section 2). Extend `compiler/rezono_compiler/rules.py` (`TYPES`), `rules_sql.py` (`SQL_TYPE`), and `rules_split.py` (`export_select`/`decode`) with `rational`, stored in SQL as reduced `(n BIGINT, d BIGINT)` with `d > 0` using `calc_sql.DUCKDB_MACROS`, `calc_sql.feldera_functions()`, and `udf/udf.rs`.
  - Replace the single-cut `partition_at_calc` with per-derivation stratification across `derived` and `functional` relations: cycles through any functional derivation, negation, or aggregation remain refused (`not_stratified` / `R009`), while acyclic interleaving (`Bool` recursion -> functional A -> `Bool` B -> functional C) is permitted.
  - **Access boundary extended:** today `compiler/rezono_compiler/pack.py` and `checker/rezono_checker/rules.py` refuse dependencies of `may_read` on a calculation selection (not yet `may_read_full`). Extend that refusal so neither `may_read` nor `may_read_full` may depend on a `functional` derivation or `calc` selection, keeping access control strictly in the `Bool` / base relational layer so `checker/rezono_checker/access.py` keeps its independent trust boundary.
- **Witnesses (`contracts/proof.yaml`):**
  - `known(v)`: winning clause/version/candidate plus absent higher-precedence guards; for `.one()`, the single candidate plus the candidate-group digest (`count = 1`, `contributors_sha256`).
  - `unknown(reason)` / `not_applicable`: domain key plus cause (empty candidate group `count = 0` with `no_match`, empty `.min`/`.max` with `empty`, missing slot with `no_value`, absent active version with `no_version_applies`, or upstream non-known state row).
  - `invalid(reason)`: every competing distinct candidate and its proof (group digest plus candidate rows, resolved on demand or from a materialized candidate view).
- **Independent checker (`checker/rezono_checker/`):**
  - **`check.py`:** generalize `outcome_total` and `outcome_state` from 1-column base kinds to any declared closed `domain` relation (single- or multi-key); verify for every domain key that `state` matches the candidate set (`count = 0` -> `unknown no_match` or `not_applicable no_match`, `count = 1` -> `known` matching the unique value, `count > 1` -> `invalid multiple_values` with all distinct candidates matching the conflict witness); permit `state = "invalid"` with full conflict witness under `conflict_policy = publish`, while rejecting publication (`rezono:proofs` failure) whenever any `conflict_policy = block` relation contains an `invalid` row.
  - **`closure.py` (`covered`):** include the `domain` relation and every candidate and guard input relation of each `functional` derivation in snapshot closure, so omitting a candidate row can never forge `known`, `unknown`, or `not_applicable`.
  - **`access.py` and `rules.py`:** independently of `rezono_publisher` (preserving `edge/publisher/tests/test_checker_boundary.py`), a filtered role sees a functional row — and marks the functional relation `full` — only when that role reads in `full` every input relation whose absence determines the value's state (analogous to `calc_sources`/`_calc`); `rules.py` enforces that neither `may_read` nor `may_read_full` depends on a `functional` derivation or `calc` selection.
  - **`proof.py` and `transition.py`:** extend `proof.py` to verify functional and multi-candidate conflict witnesses, and extend `transition.py` from `rezono.rules/1` (`base`/`derived`) to `rezono.rules/2` `role: functional` for `rezono 1` safe steps and intermediate invariants (Section 3, item 5).
- **Three engines (honoring the five Feldera rules):**
  1. **State after recursion, never inside:** functional views are never emitted inside `DECLARE RECURSIVE VIEW`.
  2. **Closed named domain:** every functional view `LEFT JOIN`s its declared finite closed `domain` relation (never a Cartesian product of kinds and never an open domain).
  3. **`Bool` stays a plain set:** `Bool` derivations emit plain set views with zero state columns or conflict views.
  4. **Co-located `(key..., state, reason, value)` view:** both **DuckDB** (`CREATE OR REPLACE TABLE`) and **Feldera** (`CREATE MATERIALIZED VIEW`) emit one combined `NOT NULL` view per functional derivation. Non-`known` rows store a typed non-NULL sentinel in SQL, `""` in snapshot row keys, and omit `value` in structured `Value` JSON per [`contracts/value.yaml`](../contracts/value.yaml). Exact rational values use `(n BIGINT, d BIGINT)` with `d > 0` via `calc_sql.DUCKDB_MACROS`, `calc_sql.feldera_functions()`, and `udf/udf.rs`; deterministic path projections such as `Service.zone` need only a `LEFT JOIN` without `GROUP BY`; only `conflict_policy = block` adds one tiny invariant check view `WHERE state = 'invalid'`.
  5. **Feldera calculation parity first:** before emitting `rezono 1` functional views on Feldera, compare all current `rezono.calc/1` states, reasons, and witness steps on Feldera against DuckDB and the checker across the examples.
  - **Soufflé (test oracle only):** inside `compiler/tests/souffle.py`, lower the non-rational fragment (`string`, `integer`, and `boolean`, mapped as `"boolean": "symbol"`) of each functional derivation to plain Datalog relations (candidate relation + `count` + `(key..., state, reason, value)` projection) and compare against DuckDB and Feldera without adding views to Feldera pipelines.

## 5. Ten codebase corrections and resolved gaps

Each of the ten issues identified against the initial proposal is resolved directly against the repository:

### 1. The 64-view budget is per pipeline, not per module

`emit.MAX_VIEWS = 64` (and `engine.view_budget` / `engine.build_memory_mb` in deploy profiles) bounds **each Feldera pipeline**, not each author module. In `compiler/rezono_compiler/rules_split.py`, `partition()` automatically cuts a rule program across multiple pipelines (`rules-1`, `rules-2`, …) in dependency order without being constrained by module boundaries. Only an indivisible **recursive core** (a strongly connected component of mutually recursive derived relations) exceeding the pipeline budget blocks compilation (`rules_split.TooBig`). Even a single non-recursive relation above the budget compiles in a pipeline of its own with an `over_budget` warning (`rules_split.over_budget`).

Therefore, naive table-style Datalog desugaring (6–11 views per value) is not rejected because "a module cannot fit 64 views"; it is rejected because **more views cost more pipelines**, which adds Rust compilation work, `export__out` tagged-union views, inter-pipeline relay traffic, and incremental memory. Co-locating `(key..., state, reason, value)` into one view per functional derivation keeps pipeline count and cross-pipeline exports low.

### 2. Equal view count does not mean equal compile or runtime cost

A functional view does more work than a plain `Bool` set view, and two tiers of functional views have materially different operator graphs:

- **Deterministic projection functional view (`"functional"`):** e.g. `Service.zone` (`service_zone`), `Service.cluster` (`service_cluster`). Performs a `LEFT JOIN` from the closed `domain` to the slot/relation chain and synthesizes `(state, reason, value)` with `CASE` — no `GROUP BY` or distinct-count state.
- **Candidate-aggregating / precedence / rational functional view (`"functional_aggregate"`):** e.g. `chosen`, `needs`, `Product.newest_day` (`product_newest_day`), `Service.pin` (`service_pin`), `Service.runs` (`service_runs`), `flow_from_step`, and any versioned, `unless`, table, or rational derivation. Performs `LEFT JOIN` over `domain`, `GROUP BY key` with `COUNT(DISTINCT val)` / `MIN`/`MAX`, short-circuit precedence/version selection, and exact-rational UDF calls (`udf/udf.rs`) when rational arithmetic is used.

**Preserving `sum(views_by_kind) == rules_sql.views` and exact `core` budget counts (`compiler/rezono_compiler/emit.py`, `rules_split.py`, `rules_sql.py`):**

- Extend `emit.VIEW_KINDS` from `("base", "check", "seal", "relation", "witness", "outcome", "calc", "export")` to include both **`"functional"`** and **`"functional_aggregate"`**.
- In `rules_split.views_by_kind(prog, name)`, a `role: functional` relation counts `{"functional": 1, ...}` (deterministic projection) or `{"functional_aggregate": 1, ...}` (candidate-aggregating / precedence / rational) **instead of** `{"relation": 1, ...}`, with any materialized witness/candidate view under `"witness"` and any `conflict_policy = block` check view under `"outcome"`.
- **`rules_sql.views(prog, name)` remains the exact unweighted SQL view count `sum(rules_split.views_by_kind(prog, name).values())`** (1 per emitted SQL view), preserving the existing invariant between `views_by_kind` and `rules_sql.views`.
- Add **`rules_split.view_weight(prog, name)`** for `engine.view_budget` partitioning in `emit.Cost`, applying the per-kind weights `{"relation": 1, "witness": 1, "outcome": 1, "functional": 1, "functional_aggregate": 2}` to `views_by_kind(prog, name)`. For legacy `role: derived` relations, `view_weight` equals `rules_sql.views` identically.

### 3. "Or any relation depending on one" belongs to `calc_not_known_positive` in `partition_at_calc`, not `calc_aggregate`

In `compiler/rezono_compiler/rules.py`:

- **`calc_aggregate`** (inside `_check_rule`) only refuses an aggregate whose direct target atom has `role == "calc"`.
- **`calc_not_known_positive`** refuses both (a) any direct read of a `role == "calc"` relation that is negative or does not constrain `(state, reason) = ("known", "")` (inside `_check_rule`), and (b) any negation or aggregation over **any relation depending on a calculation** (`after = self.downstream(outputs)`), enforced in `Program.partition_at_calc`.

Both checks stay unchanged for `rezono 0` (`role == "calc"`). In `rezono 1`, per-derivation stratification replaces `partition_at_calc` for `functional` derivations (still refusing cycles through functional derivations, negation, or aggregation, and extending the existing `may_read` refusal so neither `may_read` nor `may_read_full` may depend on a `functional` derivation or `calc` selection).

### 4. "Lifted across strata" requires a mandatory closed domain, not an open calculation selection

In `compiler/rezono_compiler/rules.py` (`load`), every `role == "calc"` selection MUST have `world == "open"`, and `_worlds` propagates `open` to every derived relation reading it positively. Negating or aggregating over an open relation is unsound (except in `@absence`, which only describes what is recorded) because absence means unknown rather than false or empty.

Accordingly, lifting state tests (`is known`, `is unknown`, `is n/a`, `is invalid`) and aggregates across strata in `rezono 1` holds **because every `functional` derivation is required to have a finite, closed domain `D`** (Section 2):

- Declaring a `functional` derivation on an `open` kind `K` or an `open` `over D(...)` relation is **refused at compile time** (`functional_open_domain`).
- Consequently, every `role: functional` relation in `rezono.rules/2` has `world: closed` unconditionally and contains **exactly one row** `(key..., state, reason, value)` for every key in `D`.
- Reading `d(k) is unknown` / `is n/a` / `is invalid` / `is known` in a higher stratum is a **positive lookup** on the totalized state row (never negation-as-failure on a missing known value).
- Aggregating over a functional derivation follows the strict four-state semantics of [`docs/rezono/expressions.md`](../docs/rezono/expressions.md#appendix-a-truth-tables-normative) Appendix A.3 definitively: **`invalid`, `unknown`, and `not_applicable` (`n/a`) all propagate** to `count`/`sum`/`min`/`max` rather than silently skipping rows or turning `unknown` into `0`. Authors who intend to exclude inapplicable members write `.where(it is known)` explicitly. For `rezono.rules/2` aggregates, `checker/rezono_checker/evaluate.py` (`_fold`, which currently skips `not_applicable` under `docs/formal.md` §6) is aligned with this strict four-state semantics so SQL lowering and the independent checker agree identically.

Legacy `role == "calc"` inputs in `rezono 0` stay `world: open` with all existing refusals intact, and `Bool` / `T*` `role: derived` relations may still be `open` as in `rezono.rules/1`.

### 9. Pack names, Money, and currency symbols

Pack names across `contracts/pack.yaml`, `docs/publication/l0.md` §1, and all ten existing standard packs under `packs/` (`std-access`, `std-decision`, `std-explain`, `std-identity`, `std-loop`, `std-order`, `std-part`, `std-review`, `std-time`, `std-view`) use **lowercase hyphenated identifiers (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`)** with no dots. - **One pack-name form (hyphenated, never dotted):** in `rezono 1`, every pack name in `pack` and `use` follows `contracts/pack.yaml` (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`). - **Where `Money` and `€` come from:**

  - **Currency symbols (`€`, `$`, …) and currency minor-unit scales are NEVER hardcoded in compiler or evaluator code** (preserving `rezono/src/schema.ts`, which holds all currency symbols as schema data in `schema.symbols`). - **What follows in each of the three affected files:**
  1. **[`docs/rezono/v0.md`](../docs/rezono/v0.md):** keeps its existing `rezono 0` prose for `rezono 0` and adds explicit cross-reference notes in §3, §4, §4b, §5, and §5c pointing to this decision: in `rezono 1`, pack names are hyphenated (`use std-money`, `use std-units`, `use std-order`), dotted pack names in `use` are refused (`R028`), and `€` comes from `packs/std-money`.
  2. **[`decisions/language-healthcare-allowance-slice.md`](language-healthcare-allowance-slice.md):** keeps its `unit Cents = money minor EUR` slice unchanged and adds a cross-reference note pointing to this decision: its remark waiting on dotted pack-name lowering for `std.money`/`std.units` is superseded in `rezono 1` by the hyphenated standard packs `std-money` and `std-units` (no dotted pack-name lowering is built for `rezono 1`).
  3. **`examples/zorgtoeslag/facts.rezono` (and `examples/zorgtoeslag/zorgtoeslag.rezono`):** remains on `rezono 0` untouched now because `rezono/test/examples.test.ts` tests it as a `rezono 0` design module; when `examples/zorgtoeslag` migrates to `rezono 1` and receives its `pack.yaml`, its `use std.money` and `use std.units` lines change to `use std-money` and `use std-units` pinned in `pack.yaml`.

## 8. Ordered rollout

1. **Feldera calculation parity:** compare all current `rezono.calc/1` states, reasons, and witness steps on Feldera against DuckDB and the independent checker across the examples before emitting `rezono 1` functional views on Feldera.
2. **Version switch:** reader and compiler dispatch by declared `rezono` version (`0` and `1` side by side), `rezono.module/5` contract, `R027`/`R028` version checks (refusing `table priority` with `table first` hint, `rule ... when ...`, `rules` pipe blocks, and dotted `use` pack names in `rezono 1`, while keeping `table priority` silent with no `W107` in `rezono 0`), and pack language version plus derived-property metadata (`kind`, `property`) in `bundle/schema-bundle.json` (`contracts/bundle.yaml`).
3. **Functional derivation IR, checker, and engines (`rezono.rules/2`):** `role: functional` with mandatory closed `domain` (`functional_open_domain` refusal for open domains), `<k>_<d>` naming for single-key derived properties, co-located `NOT NULL` `(state, reason, value)` (including `rational` in `rules.py`, `rules_sql.py`, `rules_split.py`, and `contracts/bundle.yaml`), new core reason codes `no_match` (`not_applicable`, `unknown`) and `multiple_values` (`invalid`) in `contracts/value.yaml`, `docs/publication/l0.md`, and `publication/rezono_publication/l0.py` (leaving `no_value` exclusively for missing slots and undecided table rows), `conflict_policy`, per-derivation stratification (extending the `may_read` refusal to `may_read_full`), multi-candidate conflict witnesses, independent checker verification (`check.py`, `closure.py`, `access.py`, `proof.py`, `transition.py`, and strict four-state `_fold` in `evaluate.py`), `"functional"` and `"functional_aggregate"` view kinds in `emit.VIEW_KINDS` with `rules_split.view_weight` preserving `sum(views_by_kind) == rules_sql.views`, one co-located view per functional derivation on DuckDB and Feldera, Soufflé test oracle lowering for the non-rational fragment (`string`/`integer`/`boolean`), and cgroup v2 `peak_build_memory_bytes` + `perf_counter()` `step_latency_ms` measurements in `.github/workflows/feldera-oracle.yml` (including shard `compiler-functional`).
4. **`rezono 1` syntax and small tooling:** unified `derived` (single-key properties, multi-key declarations, `over`, `.one()`, method-form `.where(...)` / `.count(pred)` / relation-as-tuple-set, `means` + `@`), `example` blocks with `W109`, two-knowledge-date comparison, period shorthand, digit grouping underscores, Ohm-derived syntax-highlighting grammar, and `rezono fmt`.
5. **Single-pass pack rule conversion:** convert all 104 pack-owned `.dl` files once (98 across `examples/`, `packs/`, `run/packs/`, plus 6 under `build/`; standard packs first, then `build/`, `run/packs/`, and `examples/`, converting platform safe steps, the eight test files reading renamed `core.dl` relations — the four `zone_of` acceptance tests, `test_support_unknown.py`, `test_role_attributes.py`, `test_product_licence.py`, and `test_platform_safe_rounds_recorded.py` — plus `examples/platform/oracle.py`, `oracle-rows.json`, and `labels/en.yaml` in lockstep), gating `scripts/language_usage.py`'s `"Native conversion"` column on `rezono 1` derivation lowering and enforcing whole-pack equivalence with explicit intended-difference tables.

## Considered

- **Reusing `no_value` for empty `.one()` candidate sets.** Rejected: `docs/rezono/publication.md` and `compiler/rezono_compiler/rezono_table.py` already use `no_value` for missing slot values and undecided table rows; a dedicated core code `no_match` separates "inputs were known, zero candidates matched" from "an input slot had no value".
- **Allowing `functional` derivations over `open` domains.** Rejected: totalizing `(key..., state, reason, value)` over an open relation cannot distinguish absence from unknown, breaks cross-strata state tests and aggregates, and contradicts Feldera rule 2; `role: derived` (`Bool`/`T*`) remains available for open relations.
- **Emitting `W107` for `table priority` in `rezono 0`.** Rejected: no repository pack uses `table priority`, `rezono 0` is the internal workbench whose conformance and lowering tests (`T04.yaml`, `test_lower_table_policy.py`, `test_rezono_1_version_switch.py`) assert clean `rezono 0` behavior, and the external phased-deprecation commitment of `v0.md` §4b starts at `rezono 1`.
- **Supporting dotted pack names (`std.money`, `std.units`) in `rezono 1` or hardcoding `€` in code.** Rejected: `contracts/pack.yaml`, `docs/publication/l0.md` §1, and all ten existing standard packs use hyphenated lowercase names, and `rezono/src/schema.ts` keeps currency symbols strictly as schema data; hyphenated `packs/std-money` and `packs/std-units` keep one naming rule and zero hardcoded currency tables.
- **Converting all 104 pack-owned `.dl` files twice (first to `rezono 0` `rule ... when ...`, then to `rezono 1`).** Rejected: doubles the largest migration and parity-testing effort in the repository for a workbench syntax that will not be part of the first public release.
- **Lowering `rezono 1` functional derivations by naive table-style Datalog desugaring into `rezono.rules/1`.** Rejected: multiplies views by 6–11× per value, inflating pipeline counts, cross-pipeline exports, and Feldera build memory, and cannot represent multi-key derived domains or published multi-candidate conflict findings cleanly.
- **Keeping `table priority` in `rezono 1`.** Rejected: implicit tie-breaking from enum declaration order makes schema ordering silently alter rule outcomes; `table first` makes precedence explicit in the table itself.
- **Allowing `may_read` / `may_read_full` to depend on functional derivations.** Rejected: keeps `checker/rezono_checker/access.py` small and avoids circularity between reading a value's state/reason and deciding whether a role may read that value.
