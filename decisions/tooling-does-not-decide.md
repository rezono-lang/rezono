# Move decisions out of repository scripts and CI workflows into shared pack forms

The [vision](../docs/vision.md#rules-not-scripts) says: "No production code walks a graph, sums a column or picks a winner. Code may read input, render output from derived rows, apply a plan, and observe. It does not decide." [AGENTS.md](../AGENTS.md) rules 1, 2 and 7 state the same constraint: no domain knowledge in code, everything that follows is compiled, and no bespoke code where a standard component already exists. [Code does not decide](code-does-not-decide.md) applied that rule to `loop/`, `run/` and `k8s-admission/`. This decision supplements it for repository tooling under `scripts/` and workflow expressions under `.github/workflows/`, without replacing [code does not decide](code-does-not-decide.md) or redefining what [build reconciliation](build-reconciliation.md), [claim release](build-claim-release.md), [decision heads](decision-heads.md) and `std-loop` already specify.

An audit at commit `0d1a379d` inspected every non-test Python script in `scripts/` (20 scripts, plus the CI-invoked budget gate `scripts/test_error_code_budget.py`) and every `if:` condition across `.github/workflows/*.yml`. Many of those scripts and workflow conditions repeat the same five decision shapes in hand-written Python dictionaries, regex classifiers, numeric comparisons and YAML conditionals. This decision defines one canonical pack home for each of the five recurring decision forms, puts the component/test dependency graph of `scripts/components.py` first in the migration queue, assigns one fate to every script and workflow condition group, and establishes a strict **no-Python-fallback, fail-closed safe state** policy once a decision moves to a pack.

## 1. The four fates and the strict reading of deciding

The four fates match [code does not decide](code-does-not-decide.md#1-the-four-fates):

- **(a) Retire.** The script or condition duplicates a rule already derived by a standard pack or `build/`, and once the pack rule takes over the old Python decision code is deleted rather than kept as a fallback.
- **(b) Independent oracle.** Only tests use the module, and it computes an independent answer that verifies a rule, a compiled artifact, a release archive or a build publication from outside the pack it checks. It lives under the component's `tests/` directory, never runs as a production fallback, and receives an entry in [the formal foundations, section 11](../docs/formal.md#11-independent-oracles).
- **(c) Pack rule.** Production tooling or CI needs the decision, and today Python code or a workflow `if:` expression makes it. Reading inputs, parsing files, launching processes or network traffic and executing a derived plan remain thin code `(d)`; the decision itself moves into one of the five shared decision forms below, and hardcoded exceptions or vocabularies become pack facts ([AGENTS.md](../AGENTS.md) rule 1). Once the pack rule is live, the replaced Python decision code is retired `(a)` or moved into `tests/` as an independent oracle `(b)` — never retained as a runtime fallback.
- **(d) Keep as thin reader-executor.** Only reading or parsing inputs, rendering outputs from derived rows of a checked publication, launching processes or network traffic, structural input-integrity checks and executing an already-derived plan. A script that still decides during a scheduled comparison period under [build reconciliation](build-reconciliation.md) is marked **(d), transitional** until that cutover completes.

**Strict reading of deciding.** Any comparison, classification, selection, threshold or count that leads to an outcome counts as deciding — even inside a script whose bulk is reading, packaging or executing. Only I/O, parsing, rendering, process/network execution and structural input-integrity checks qualify for `(d)`. Hardcoded exceptions such as `rezono-*` and `pip` in `scripts/check-pinned.py` and `scripts/venv-reuse.py`, topic verbs in `scripts/release-notes.py`, package lists in `scripts/release-wheel.py` and task-ID lists in `.github/workflows/disposable-cluster.yml` are domain/repository knowledge and move to pack facts.

### 2.1 Monotonically shrinking budget (`packs/std-budget`)

`std-loop` models reconciliation sweeps, tokens, rounds and fixed points across runs; a keyed numeric ceiling and base-to-head ratchet has no sweep, round or step. Following Rezono's pattern of one small standard pack per reusable concept (`std-order`, `std-time`, `std-decision`, `std-review`, `std-access`), the shrinking-budget rules live in a dedicated standard pack `packs/std-budget` (registered under [standard pack names](standard-pack-names.md)) and imported by `build/`.

- **Inputs.** `BudgetEntry(id, budget, cell, ceiling, revision)` and `BudgetReading(id, budget, cell, observed, revision)` where `revision` is `"base"` or `"head"` and counts are whole integers.
- **Derived relations.**
  - `budget_raised(budget, cell)`: the head ceiling exceeds the base ceiling (including a new cell whose base ceiling is absent, treated as `0`).
  - `budget_exceeded(budget, cell)`: the head observed count exceeds the head ceiling (including an observed cell without a head ceiling).
  - `budget_ratchet_violation(budget, cell)`: the head observed count exceeds the base observed count, so slack left behind by an earlier fix cannot hide a new finding (as [compiler error codes](compiler-error-codes.md) and `scripts/leak_check.py` require).
  - `budget_slack(budget, cell)`: the head observed count is strictly below the head ceiling (an advisory hint to lower the listed ceiling, never a blocker).

### 2.2 Commit-pinned evidence (`packs/std-review`)

`packs/std-review` already binds every `Review` to exact `content_sha256` and `support_sha256` hashes and derives `review_current` and `change_stale` ([review and rights](review-and-rights.md)). Commit-pinned CI evidence uses the exact same currency principle over a 40-character Git commit SHA:

- **Inputs.** `EvidenceRequirement(id, change, evidence_kind, commit_sha)` and `EvidenceAttestation(id, change, evidence_kind, commit_sha, outcome, source)` where `outcome` is `"passed"` or `"failed"` and `source` is non-empty.
- **Derived relations.**
  - `evidence_current(change, evidence_kind, commit_sha)`: a `"passed"` attestation with a non-empty `source` exists for the exact `(change, evidence_kind, commit_sha)`, and no `"failed"` attestation exists for that triple.
  - `evidence_stale(change, evidence_kind, commit_sha)`: a requirement exists at `commit_sha`, a `"passed"` attestation exists for `(change, evidence_kind)` at a different commit SHA, and `evidence_current` does not hold at `commit_sha`.
  - `evidence_missing(change, evidence_kind, commit_sha)`: a requirement exists at `commit_sha` and `evidence_current` does not hold.

Every push to a new commit SHA invalidates prior attestations automatically without script-specific staleness logic.

### 2.3 Change-to-target selection (`build/`, starting with `scripts/components.py`)

[Build reconciliation](build-reconciliation.md) already defines `build_selected_job(run, component, reason)` and `build_full_selection(run, reason)`, but today the repository's file-consumer graph, shared-reader map, full-selection paths and job-input map still live as Python tables (`FILE_CONSUMERS`, `PR_FILE_CONSUMERS`, `TERMINAL_CONSUMERS`, `PR_DEFERRED_DEPENDENTS`, `SHARED_READERS`, `PACK_READERS`, `FULL_SELECTION_PATHS`, `JOB_INPUTS`, `PR_TEST_LEAVES`, `LANGUAGE_COVERAGE_LEAVES`, `SHARDS`, `PARALLEL`) inside `scripts/components.py`.

Moving `scripts/components.py`'s dependency tables into `build/` **comes first** after the shared forms:

- **Pack facts in `build/`.** Component/file consumers (`BuildFileConsumer`), shared path readers (`BuildSharedReader`), full-selection trigger paths (`BuildFullSelectionPath`), job-input readers (`BuildJobInput`), component job capabilities (`needs_oracle`, `needs_full_history`, `needs_worker_seed`), and auxiliary CI target rules (`BuildTargetRule(id, target, path_prefix, kind)` with `kind` in `"direct"` | `"full_fallback"`).
- **Derived relations in `build/`.** `build_selected_job(run, component, reason)` and `build_full_selection(run, reason)` derive the component and test selection directly from `build/` pack facts, manifest observations and verified receipts — never by reading Python tables from `scripts/components.py`. Auxiliary targets (`cluster-suite`, `role-publication`, `feldera-oracle`, fast-check sampling) share `build_target_selected(run, target, reason)` and `build_target_not_required(run, target)` over the same verified cut and changed-path observations.
- **What stays thin code `(d)`.** Reading the Git diff, walking the repository tree, reading regular manifest blobs and writing the workflow matrix JSON remain thin Python adapters.

### 2.4 Single-effect watchdog (`packs/std-loop`)

`packs/std-loop` already derives `current_sweep`, `deadline_until` and `deadline_expired` (`quiet_round.dl`) and complete-sweep receipts (`complete_sweep.dl`). Both `scripts/standstill.py` and `scripts/release_claims.py` (whose claim-specific rules already live in `build/rules/claims.dl` and `build/rules/claim_release.dl` under [claim release](build-claim-release.md)) share one single-effect watchdog form in `packs/std-loop`:

- **Inputs.** `WatchdogTarget(id, run, cut_tick, window_seconds, work_pending, receipt)` (`work_pending` in `"yes"` | `"no"`, `window_seconds` supplied from an effective `std-decision` record), `WatchdogActivity(id, target, activity_tick)` and `WatchdogActiveEffect(id, target, created_at)`.
- **Derived relations.**
  - `watchdog_trigger(run, target, reason)`: the target has a matching `LoopSweepReceipt` at `(run, cut_tick)`, `work_pending` is `"yes"`, no `WatchdogActiveEffect` exists for `target`, and either no activity was observed or the latest `activity_tick + window_seconds <= cut_tick`.
  - `watchdog_resolve(run, target, effect, reason)`: the target has a matching `LoopSweepReceipt`, a `WatchdogActiveEffect` exists at `created_at`, and an observed `WatchdogActivity` has `activity_tick > created_at`.
  - `watchdog_hold(run, target, reason)`: names why no effect fires — `"receipt-missing"` (unknown is explicit, never trigger without a receipt), `"no-pending-work"`, `"within-window"` or `"effect-already-open"` (guaranteeing at most one active effect).

### 2.5 Who may change what (`packs/std-review` + `packs/std-access`)

`packs/std-review` already imports `packs/std-access` and checks `may_review(role, kind, element)` against `RoleGrant` in `authority.dl`, while `packs/std-access` already declares `may_propose(role, kind, element)`, `may_publish(role, kind)` and `may_execute(role, plugin)`. Extending `packs/std-review` with the symmetric proposer-side check gives one shared home for change authorization, policy gates and advisory findings:

- **Inputs.** `ChangeProposal(id, change, role, day)` alongside `std-review`'s `Change`, `ChangeMember`, `RoleGrant` and `ReviewPolicy`, and `std-access`'s `may_propose` / `may_review` / `may_publish` / `may_execute` grants.
- **Derived relations.**
  - `change_member_unauthorized(change, member)`: the proposal's author lacks an active `RoleGrant` for `role` on `day`, or `may_propose(role, kind, element)` does not hold for that `ChangeMember` (covering worker vs planner protected paths in `scripts/red_guard.py`, forbidden branch/message disclosures in `scripts/leak_check.py`, and GPL indicators in `scripts/release-audit.py`, where no role holds `may_propose`).
  - `change_authorized(change)`: a `ChangeProposal` exists for `change`, no member is in `change_member_unauthorized`, and `unreviewed_required(change)` does not hold.
  - Advisory taste findings (`scripts/pack_warnings.py`, single-commit squash-subject hints in `scripts/release-notes.py`) use `ReviewPolicy(policy="mark")` so `unreviewed_marked` reports findings without blocking merge ([AGENTS.md](../AGENTS.md) rule 5).

## 5. Explicit boundaries, fail-closed safe state and migration order

1. **Checker and independent oracles stay an independent second path.** Moving decisions into packs never merges an oracle (`scripts/convert_pack.py`, `compiler/ci/verify_feldera_run.py`, `scripts/role_publication_ci.py` isolation assertions, `k8s-admission/` oracles, Souffle/DuckDB/Feldera oracles) into the rules it checks ([AGENTS.md](../AGENTS.md) rule 6).
2. **Compiler and engine evaluate each other only via a pinned earlier commit of `main`.** As [build reconciliation](build-reconciliation.md) requires, the pack, compiler, engine, dependencies and checker that judge a pull request or merge group always execute from a pinned protected-main checkout, never from candidate code under test.
3. **Executing effects stays thin code `(d)`.** Only the decision, classification or selection moves into a pack rule. Reading Git trees and diffs, parsing YAML/TOML/AST/JUnit XML, running pytest/Node/git/gh, opening or closing issues, issuing conditional `git push --force-with-lease` deletes and uploading workflow artifacts stay small adapters consuming verified derived rows.
4. **No Python fallback; fail-closed safe state on missing or rejected publication.** Once a script's decision moves into a pack rule, the old Python decision code is **retired `(a)`** or moved into `tests/` as an **independent test oracle `(b)`** — it is never kept as a runtime fallback. If the pack publication is absent or rejected by the checker, every consumer enters its **fail-closed safe state** (never less checking, never an unverified effect):
   - **CI suite selection:** run **all** suites (`build_full_selection`), never a narrowed subset.
   - **Task claims:** leave every claim untouched; never delete a claim without a verified publication.
   - **Task dispatch / orchestration:** assign no new tasks and report a finding.
   - **Policy, budget, evidence and release gates:** fail closed (block merge or publish) and report a finding; watchdogs perform no unverified side effect and report a finding.
5. **Migration order.**
   - **Step 1 — Shared decision forms first:** Implement the five canonical forms (`packs/std-budget`, `packs/std-review` commit-pinned evidence and proposer authorization with `packs/std-access`, `packs/std-loop` single-effect watchdog, and `build/` target selection rules).
   - **Step 2 — `scripts/components.py` dependency graph -> `build_selected_job`:** Move `FILE_CONSUMERS`, `PR_FILE_CONSUMERS`, `SHARED_READERS`, `FULL_SELECTION_PATHS`, `JOB_INPUTS` and related tables into `build/` facts and rules so `build_selected_job` derives its graph from the pack rather than Python tables. Complete the transition comparison under [build reconciliation](build-reconciliation.md), then move the Python selector to a test oracle `(b)` or retire `(a)` — leaving no runtime Python fallback.
   - **Step 3 — Individual scripts and workflow `if:` gates:** Migrate individual scripts (`scripts/check-pinned.py`/`venv-reuse.py`, budget scripts, guard/evidence scripts, watchdogs and release scripts) and workflow `if:` blocks **strictly after** the `build/` cutover and decision-driven work tasks have landed, retiring `(a)` or moving to test oracles `(b)` each replaced Python decision path as it switches.

## Considered

- **Migrate each script into its own bespoke pack or Datalog file.** That would duplicate the same five patterns (shrinking budgets, commit-pinned evidence, change-to-target graphs, single-effect watchdogs and change authorization) across twenty files instead of proving each form once in a standard pack.
- **Put shrinking budgets inside `packs/std-loop`.** `std-loop` models reconciliation sweeps, tokens, rounds and fixed points across ticks. A revision-to-revision numeric ceiling and ratchet has none of those concepts and fits a dedicated small standard pack `packs/std-budget`, matching `std-order`, `std-time` and `std-decision`.
- **Keep Python scripts as a runtime fallback when the pack publication is missing or rejected.** Maintaining a second live decision path in Python duplicates policy, invites silent drift from pack rules, and violates the single-source-of-truth principle. Failing closed to the safe state (CI runs all suites, claims stay untouched, no new tasks are dispatched, policy and release gates fail closed, and a finding is reported) is simpler and strictly safer; former Python decision code stays only as retired code `(a)` or an independent test oracle `(b)` in `tests/`.
- **Eliminate top-level GitHub Actions `if:` guards on privileged workflows.** Runner-level `if:` checks prevent untrusted forks or actors from even starting a runner; moving the authorization decision into `packs/std-access` makes the policy explicit and reviewable while keeping the workflow `if:` as defence-in-depth launch gating.
