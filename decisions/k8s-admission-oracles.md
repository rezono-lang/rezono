# Kubernetes admission oracles

Use cel-go (Apache-2.0) as a standalone expression evaluator with explicitly typed request, object and parameter environments. Run the same hand-authored cases through Rezono and CEL on every PR, asserting both against independently stated answers. Use the upstream Kubernetes apiserver admission policy evaluator and matcher (Apache-2.0) in an in-process offline harness with typed fixtures and an in-memory parameter store. Load complete policy and binding manifests including their match rules, failure modes and parameter lookup. Reusing the evaluator alone would miss binding failures. Both harnesses are development dependencies. Pin and lock their modules when introduced.

The disposable cluster supplies the end-to-end oracle. Submit server-side dry-run requests as the fixture identity, check admission status, denial details and policy type-checking warnings, and include the unknown-input cases. Keep these tests in the admission component with the shared cluster marker. The reconciliation component owns the shared workflow. Compilation work starts only when both rules pass all three oracles.

Target the stable admissionregistration.k8s.io/v1 policy API in Kubernetes 1.30. The reference declares validation expressions, messageExpression, failure policy, parameter references and parameterNotFoundAction. Its exact bytes have SHA-256 6ea3e9c8411c055792436143187403e6f0d5da336f3534ea183b36c3c4f1e473.
