# How to emit firewall rules

The zone-to-zone projection provides an overview. Applying it as policy would permit unrelated services sharing a zone and a port. Emit one allowance per distinct crossing flow, retaining source, destination and function as evidence. Each row contains an inclusive source node range (sourceFrom, sourceTo), a single destinationAddress, protocol and inclusive fromPort and toPort. Sort by source, destination, function, protocol and port. Two flows that authorize identical packet fields keep separate evidence. A packet is permitted when any allowance matches.

Assign disjoint integer IPv4 ranges to source networks. Each endpoint has a unique address in its attached network's range, including hosted control endpoints on management. The authored scenario uses documentation addresses and explicit fixture protocols. These values are only inputs for the simulation. Versioned product evidence will supply real transport properties for the product example.

The static expectations include each distinct source, destination, protocol and port with a desired crossing as a positive case. For each rule, vary the service on the same source cluster and the destination within the same destination zone while retaining transport. A different destination blocked by all rules yields a negative case. An unrelated source that inherits an allowance for a target yields an excess-access finding. Its witness includes the intended source and function. Count each excess tuple once across witnesses. All checks concern cross-zone policy decisions. Check coverage and use independently by matching packet fields, and require empty uncovered and unused sets. The simulated case set can be compared to an observation only once an appropriate recorded run exists.

For in-zone pod traffic, use Kubernetes networking.k8s.io/v1 NetworkPolicy. Give each modeled zone its own namespace and identify pods by the rezono.org/service label. Emit a namespace-wide baseline selecting all pods with both ingress and egress isolation, then matching ingress and egress allowances for the exact peer and transport. Set endPort only for a range. Service and namespace labels are prerequisites for applying these example policies. Cross-zone enforcement belongs at the firewall. A single vendor configuration would bind the example to a particular firewall.

## Fixed IPv4 egress

The second simulation assigns a unique source IPv4 address from a separate egress pool to each gateway-managed workload. Its rule uses that address as both source bounds. The fixture names workload and fleet-agent endpoints subject to the gateway. External clients, storage and node-originated traffic retain their ordinary source ranges. Separate pools prevent a gateway address from matching a node-range rule. The output retains the coverage, use, positive, negative and excess-access evidence for each simulation.

This stage requires Cilium egress gateway, BPF masquerading and Cilium kube-proxy replacement. A hosted k0smotron control plane must have kube-proxy disabled. All expectations assume these IPv4 prerequisites. Hubble observations from a future run can test the source address actually seen at the boundary.
