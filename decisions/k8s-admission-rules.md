# Two namespace admission rules

Apply the platform example's verified supply and in-zone flow decisions to Pod images and NetworkPolicy ingress. Both accept a single request using a namespace publication. The latter exercises correlated tuples. A writer-identity rule was considered, but admission identity cannot be reconstructed by reading the resulting object.

For supply, join build and signature evidence for the same immutable image digest, the service and its namespace. The platform example's service-level result alone cannot authorize a particular image. A service field binding must identify the workload for comparisons. Compare complete digest-qualified image references for every regular, init and ephemeral container on Pod CREATE and UPDATE, including the ephemeralcontainers subresource. A missing required service binding yields a missing-field diagnostic. Empty optional container groups impose no obligations.

For flow, project the example's in_zone_policy(source, destination, port) into same-namespace TCP ingress in managed namespaces. Use a closed NetworkPolicy shape with an exact service label for the target and each same-namespace pod peer, numeric TCP ports and ingress-only policyTypes. Accept an empty ingress list as isolation. Reject unsupported selectors, peer forms, wildcards, protocols, ranges and egress-bearing policies. Require every pair in the Cartesian product of peers and ports of each ingress entry to match one published tuple. Future selector forms require their own meaning and fixtures.

## Hand-calculated fixtures

Use namespace sample, service web and two immutable test images A and B. Publish A and B for web. A Pod running A passes, as does a Pod running A with init image B. An unsigned image C alone or as one additional container fails. The same A in a namespace without a publication fails. Publish flow tuples (reader, web, 443) and (probe, web, 8443). Each corresponding single-peer policy passes. An isolation policy passes. The crossed tuple (reader, web, 8443) fails, as does one ingress entry containing both peers and both ports. A missing target service label is reported separately from a known disallowed tuple.

## Publication and failure

Use one namespaced, structurally validated parameter CRD with a required lowercase SHA-256 publication digest, unique service/image entries and unique source/destination/port entries. Bound the parameter collections and reject unknown fields on submission. Generate sorted entries from one verified publication and replace the object atomically. Advance only after all inputs have been validated. The last accepted parameters continue to work when the producer is unavailable. Restrict parameter writes and policy and binding changes to the reconciliation identity.

Bind rules by namespace scope to a named parameter in the request namespace. Use Deny validationActions, failurePolicy Fail and parameterNotFoundAction Deny. For normal validation failures use separate guarded validations for missing input and violated membership with the rule identifier and digest in messageExpression. Generate immutable release-specific policy and binding names that identify the rule and release even on Kubernetes-generated parameter lookup or evaluation errors. Check the actual API status, including these identifiers, in the live oracle. Stage versioned parameter objects and bindings before retiring prior enforcement. Mixed releases may temporarily deny requests, never broaden permissions.

Preflight records the derived entries and proof. For observations, recover the same fields by inverting the render binding and record drift with publication and observation witnesses. IPv6 arithmetic and other unsupported operations remain observation-only. After all three oracles agree, a compiler may split typed rule IR into model-only parameter projections and single-object CEL. Reject cross-object reads during admission compilation with a diagnostic. Retain manual expressions as test expectations.
