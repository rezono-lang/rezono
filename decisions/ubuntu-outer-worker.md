# Ubuntu outer worker bootstrap and acceptance

Use Ubuntu Server 24.04 LTS with NoCloud cloud-init for both disposable acceptance trials. The independent Flatcar run at `0bf39a85db9aaed5ea7a72156c6c7c36f03c15c5` observed the outer worker Ready and the same lease renew again 20.430698 seconds later. Its inner VMI was Ready and Running. The guest console returned exactly one matching marker in 575 lines over 37 reads. The libvirt-domain ownership check returned `vmi_uid_mismatch` before the first vCPU statistics sample. The console evidence stands; acceleration of that guest remains unproven. This concludes the Flatcar attempt series. Both Ubuntu live observations are pending. ## Offline boot boundary

Use the recorded Noble amd64 cloud image with SHA-256 `04e8f2461a16a44e78a370284471f29616cdd9baf1893df25807b71f985b6c94`. The image acquisition boundary verifies the downloaded bytes before handing the local disk to the launcher. The catalog digest and provenance are in the [original host decision](flatcar-worker-host.md). Stage the pinned k0smotron renderer and seed tooling during dependency preparation. The offline test consumes the prepared tools and never contacts a controller or cloud provider. [Pinned cloud-init provisioner](https://github.com/k0sproject/k0smotron/blob/c23391b08842d8b824e40e1324267f08b923f743/internal/provisioner/cloudinit.go)

The Ubuntu path in the live trial calls the same outer-worker launcher that the offline test exercises. In `run/probes/worker-join/ubuntu_worker.py`, `launch(workdir, machine_id, bootstrap_bytes, *, acquire_image, start_qemu)` obtains the verified disk from `acquire_image(url, sha256)` and passes final QEMU arguments to `start_qemu(argv)` while the files exist. Render the supplied synthetic or short-lived bootstrap input through k0smotron's cloud-init provisioner. Attach the resulting user-data and machine-specific instance ID and hostname on an ISO9660 seed labeled `cidata`. Keep the bootstrap file owner-only and pass its path to k0s. An offline probe inspects the attached disk for two distinct machine identities. It substitutes the image download and QEMU process start. The renderer and disk producer run normally. The inner guest's separate NoCloud disk serves only the inner guest. [NoCloud datasource](https://github.com/canonical/cloud-init/blob/9dfa068353b2d6477276ac675faf4fc5e046b5dc/doc/rtd/reference/datasources/nocloud.rst)

## Live observations

1. Start a fresh runner-local controller with no registered nodes and boot the outer Ubuntu worker with its seed. Require the expected Ubuntu OS, node UID and label, matching kubelet version, Ready, and two increasing renewal times on the same node lease.
2. Use that Ubuntu host for KubeVirt. Bind the Ready, Running VMI to its node, active launcher and running compute container. Verify the guest's firmware identity on its serial console. On the same active KVM domain, require stable domain UUID and runtime ID, matching VMI ownership and two increasing live vCPU samples. Re-read the identities after sampling. A missing or mismatched identity leaves the trial unproven.

Keep the trials disposable and independent of provider credentials. Both live results are required before selecting Ubuntu for a provider deployment.
