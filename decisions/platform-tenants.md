# Tenant requests, delivery and catalog publication

Two fictional teams, Elm and Reed, submit versioned request files under an example pack's teams directory. Each path identifies the team and service. In CI the request is the file. Backstage occupies the base cluster behind the entry service and uses the identity provider for login. Its template creates a Forgejo branch and proposal. That credential has no merge permission. Repository review controls decide admission. After merge the hub reconciles the approved plan and returns observed delivery status to the proposal.

Order accepted request-history entries by immutable submission time, breaking simultaneous submissions by team and service. The ordinal within each team forms the delivery identifier. The example previews submitted requests in this order. Preserve the ordered history when adding a new request. Use integer quantities for cores, GiB and EUR cents per month. Show requested cost separately from admission and actual expenditure. The capacity ledger charges a delivery when its merge receipt appears in the base revision. A combined proposal tests all admissible changes in submission order against that ledger. A successful preview changes the proposed total only.

Production allows medium sizes and sends unlisted external connections for review. Development allows small sizes and denies unlisted connections. Matrix entries permit a matching connection by default. A cross-tenant connection additionally requires both a reciprocal request and a recorded approval for the named destination and port. Resolve the destination's owner and zone from the proposed delivery. An isolation finding records the missing conditions. A denied connection or insufficient capacity blocks the proposal. Review holds an otherwise admissible proposal.

The catalog supplies cluster and managed database sizes. A guest cluster implies hosted control and virtual workers. A database is delivered in that guest cluster. The proposed inventory associates the tenant with its identity organization, secret policy, registry project and GitOps project. The apply target relation lists only that tenant's delivery clusters. Keycloak, OpenBao, Argo CD and CloudNativePG are product choices for those roles. The standalone calculation uses the catalog's attributes to produce rows. An additional team or a size is a data change.

One Backstage Component descriptor is generated for each requested service, under its owning namespace. Tenant publication selects only owned rows. The catalog descriptor and the proposed delivery are previews. A reconciled publication requires observed state. Step state, waiting time and completion time must come from the recorded loop evidence. No elapsed time is inferred from a request.

## Independent acceptance examples

Elm requests a production cluster and database for 7,505 EUR cents per month. Its external connection requires review. Reed requests a development cluster for 2,495 cents. Its unilateral connection to Elm's database is denied. With the first request held for review and the second denied, landed usage is zero. The third small request fits and still charges nothing until it lands. With six cores, 12 GiB memory and 70 GiB storage already landed, each of two additional small requests fits individually. Their combined candidate exceeds the three limits by one core, two GiB memory and ten GiB storage. The committed row sets include the proposed inventory, publication components, tenant-scoped targets, decision evidence, capacity and costs for both scenarios.
